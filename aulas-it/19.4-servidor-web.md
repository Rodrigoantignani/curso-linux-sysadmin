## 1 · Riscaldamento

1. Due processi possono ascoltare sullo stesso indirizzo e sulla stessa porta senza un meccanismo esplicito di condivisione?

2. Un processo attivo garantisce che il nome richiesto selezioni il sito che avevi in mente?

3. Un file leggibile dall’amministratore è necessariamente leggibile dal processo web?

## 2 · Perché conta

Il browser mostra una pagina. Non sai ancora quale server abbia risposto, quale sito sia stato selezionato o da dove provenga il contenuto. Una pagina di benvenuto può nascondere un nome errato.

In questa lezione nginx riceve il traffico isolato e Apache ascolta soltanto sul loopback. Puoi confrontare i processi senza provocare una contesa per la porta pubblica.

### Ponte Windows

Pensa alla combinazione indirizzo, porta e nome come reception, sportello e destinatario. Il browser consegna il nome nella richiesta; raggiungere la reception non seleziona da solo il destinatario.

## 3 · Modello mentale

![Nome, porta e radice rispondono a domande diverse](../img/19.4-nome-porta-e-raiz.it.jpg)

*Il nome sceglie il sito; percorso e permessi decidono il file.*

L’ascolto decide dove il processo riceve connessioni. L’intestazione `Host` partecipa alla selezione del sito HTTP. La radice traduce il percorso richiesto in un file.

Le directory antenate devono permettere l’attraversamento all’utente del servizio. Il permesso di lettura sul file finale non compensa una directory precedente inaccessibile.

Nel lab `http://www.lab.test/` raggiunge nginx. Il percorso `/apache/` viene inoltrato ad Apache locale; le due connessioni avranno registri distinti.

Non incollare la configurazione principale Debian su Rocky. Leggi prima la configurazione caricata e il manuale della famiglia; nomi degli utenti e punti di inclusione cambiano.

## 5 · Lab guidato

### Passo 1 · Installare senza esporre la gestione

**Ipotesi:** L’installazione può avviare un servizio prima che tu ne limiti l’ascolto?

```bash
set -eu
test ! -L /etc/m19-lab.env
test "$(stat -c '%U:%G:%a' /etc/m19-lab.env)" = root:root:644
cat /etc/m19-lab.env
. /etc/m19-lab.env
test "$LAB_IP" = 192.0.2.204
ip -4 -o address show dev "$LAB_IF" | grep -F '192.0.2.204/24'
for pkg in nginx apache2; do
  if dpkg-query -W -f='${Status}' "$pkg" 2>/dev/null | grep -q 'install ok installed'; then
    printf '%s\n' "STOP: $pkg already installed" >&2; exit 1
  fi
done
test ! -e /etc/nginx/nginx.conf
test ! -e /etc/apache2/apache2.conf
for unit in nginx apache2; do
  test "$(systemctl is-enabled "$unit" 2>/dev/null || true)" != masked
done
EVID=/root/m19a4
test ! -e "$EVID"
install -d -m 700 "$EVID"
systemctl mask nginx.service apache2.service
apt-get update
apt-get install -y nginx apache2 curl
cp -a /etc/nginx /etc/apache2 "$EVID/"
```

**Output atteso:** I pacchetti sono installati; le unità restano mascherate. Se un controllo interrompe il lavoro, indaga prima di proseguire.

**Verifica:** Conferma che l’interfaccia sia quella isolata e che la console resti accessibile. Un blocco dell’installazione richiede di risolverne la causa, senza smascherare il servizio incompleto.

### Passo 2 · Preparare contenuto dedicato

**Ipotesi:** Quale utente deve leggere il file e attraversare le directory?

```bash
test ! -e /srv/www/m19-web
install -d -m 755 /srv/www/m19-web
printf '%s\n' 'M19 web: OK' > /srv/www/m19-web/index.html
chmod 644 /srv/www/m19-web/index.html
namei -l /srv/www/m19-web/index.html
runuser -u www-data -- cat /srv/www/m19-web/index.html
```

**Output atteso:** Il lettore del servizio ottiene il marcatore del lab senza diventare proprietario dell’albero.

**Verifica:** Registra proprietario e modo. Il contenuto statico non richiede che il processo web possa scrivere nella radice pubblicata.

### Passo 3 · Separare la porta di Apache

**Ipotesi:** Un ascolto sul loopback deve risultare raggiungibile da un’altra VM?

```bash
printf '%s\n' 'Listen 127.0.0.1:8081' > /etc/apache2/ports.conf
a2dissite 000-default
cat > /etc/apache2/sites-available/m19-web.conf <<'EOF'
<VirtualHost 127.0.0.1:8081>
    ServerName www.lab.test
    DocumentRoot /srv/www/m19-web
    <Directory /srv/www/m19-web>
        Require all granted
    </Directory>
    ErrorLog /var/log/apache2/m19-error.log
    CustomLog /var/log/apache2/m19-access.log combined
</VirtualHost>
EOF
a2ensite m19-web
apache2ctl configtest
```

**Output atteso:** Il controllo di sintassi accetta la configurazione; il servizio è ancora mascherato. Un avviso sul nome globale va distinto da un errore fatale.

**Verifica:** Leggi l’intero file delle porte. Non conservare una seconda direttiva di ascolto pubblico lasciata dal pacchetto.

### Passo 4 · Selezionare il sito su nginx

**Ipotesi:** Come impedisci che un nome errato riceva per caso la pagina corretta?

```bash
test -z "$(find /etc/nginx/conf.d -maxdepth 1 -name '*.conf' -print -quit)"
cat > /etc/nginx/nginx.conf <<'EOF'
user www-data;
worker_processes auto;
pid /run/nginx.pid;
error_log /var/log/nginx/error.log;
include /etc/nginx/modules-enabled/*.conf;
events { worker_connections 512; }
http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;
    include /etc/nginx/conf.d/*.conf;
}
EOF
cat > /etc/nginx/conf.d/m19-web.conf <<EOF
server {
    listen $LAB_IP:80 default_server;
    server_name _;
    return 404;
}
server {
    listen $LAB_IP:80;
    server_name www.lab.test web.lab.test;
    root /srv/www/m19-web;
    index index.html;
    allow 192.0.2.0/24;
    deny all;
    access_log /var/log/nginx/m19-access.log;
    error_log /var/log/nginx/m19-error.log;
    location /apache/ {
        proxy_pass http://127.0.0.1:8081/;
    }
}
EOF
nginx -t
systemctl unmask nginx.service apache2.service
systemctl enable --now apache2 nginx
```

**Output atteso:** nginx occupa soltanto l’indirizzo isolato sulla porta 80; Apache occupa soltanto il loopback sulla 8081.

**Verifica:** Se esiste un firewall precedente, adatta una regola limitata all’interfaccia e alla rete isolate con la procedura della 19.1; non cancellare regole e non aprire la zona di gestione.

### Passo 5 · Collegare richiesta e registri

**Ipotesi:** Lo stesso file ottenuto da due percorsi dimostra che i processi coincidono?

```bash
ss -ltnp '( sport = :80 or sport = :8081 )'
curl --fail --resolve www.lab.test:80:192.0.2.204 http://www.lab.test/
curl --fail --resolve www.lab.test:80:192.0.2.204 http://www.lab.test/apache/
curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: wrong.lab.test' http://192.0.2.204/
tail -n 5 /var/log/nginx/m19-access.log
tail -n 5 /var/log/apache2/m19-access.log
```

**Output atteso:** Le due richieste corrette ricevono il marcatore. Il nome non configurato riceve 404; soltanto la richiesta inoltrata raggiunge il registro di Apache.

**Verifica:** Ripeti le due richieste corrette dalla VM `201` o `202`. L’accesso esterno alla porta `8081` deve fallire perché appartiene al loopback.

![Un processo attivo non dimostra la risposta corretta](../img/19.4-processo-nao-e-resposta.it.jpg)

*Controlla la richiesta reale e la risposta prima di concludere.*

### Passo 6 · Indagare la protezione senza rimuoverla

**Ipotesi:** Se la lettura locale funziona, una politica può ancora negare il servizio?

```bash
systemctl is-active nginx apache2
journalctl -u nginx -u apache2 -b --no-pager -n 30
command -v aa-status >/dev/null && aa-status || true
stat -c '%U:%G %a %n' /srv/www/m19-web /srv/www/m19-web/index.html
```

**Output atteso:** Identifichi quali controlli siano presenti; non presumi un profilo AppArmor caricato soltanto perché usi Debian.

**Verifica:** Nel confronto Rocky leggi contesto e dinieghi prima di definire l’etichetta persistente seguente, soltanto sull’albero dedicato.

```bash
getenforce
ls -Zd /srv/www/m19-web
semanage fcontext -l | grep -F '/srv/www/m19-web' || true
semanage fcontext -a -t httpd_sys_content_t '/srv/www/m19-web(/.*)?'
restorecon -Rv /srv/www/m19-web
sudo ausearch -m AVC -ts recent || true
```

Questo blocco appartiene soltanto a Rocky con l’albero creato e senza una regola locale precedente. Se la regola esiste già, controllala invece di aggiungerne un’altra. La porta `8081` resta nel lab Debian. Nel confronto Rocky usa `8008`, dopo aver confermato che appartenga a `http_port_t`, sia libera e non serva un’altra applicazione. Configura lì Listen e VirtualHost su `127.0.0.1:8008` e adegua solo l’upstream del confronto Rocky; non cambiare il lab Debian. `8081` può essere `transproxy_port_t` e non autorizzare il bind di Apache.

Leggi `semanage port -l` e usa soltanto una porta autorizzata al processo o un’assegnazione specifica già revisionata. Non riclassificare una porta di un altro servizio e non disattivare SELinux per effettuare il confronto.

Dopo il relabel, nessuna corrispondenza AVC è il risultato atteso: ausearch restituisce 1 in questo caso. Il suffisso del comando evita un arresto con set -e; errori diversi nella lettura dell’audit devono comunque essere indagati. Controlla le porte con `sudo semanage port -l` prima del confronto Rocky.

## 6 · Rompi e ripara

Introduci un guasto per volta nella VM `204`, registra il risultato e ripristina prima del successivo. I comandi di ripristino agiscono soltanto sugli oggetti dedicati di questa lezione.

### Guasto 1 · File inaccessibile

**Sintomo:** Applica `chmod 000 /srv/www/m19-web/index.html`; la richiesta corretta riceve 403.

**Indagine:** Leggi l’errore nginx e `namei -l /srv/www/m19-web/index.html`.

**Causa:** Il modo impedisce la lettura all’utente del servizio; la selezione del sito resta corretta.

**Riparazione:** Ripristina con `chmod 644 /srv/www/m19-web/index.html`.

**Verifica:** Ripeti la richiesta con lo stesso nome e controlla il marcatore.

**Prevenzione:** Mantieni scrittura amministrativa e lettura minima del servizio, senza permessi totali.

### Guasto 2 · Backend fermo

**Sintomo:** Ferma soltanto `apache2` con `systemctl stop apache2`; `/apache/` restituisce 502.

**Indagine:** Controlla `ss`, l’errore nginx e lo stato di Apache. La radice statica risponde ancora.

**Causa:** Il frontend ha ricevuto la richiesta, ma la connessione all’upstream locale è fallita.

**Riparazione:** Esegui `systemctl start apache2`; non modificare nome o radice di nginx.

**Verifica:** Ripeti il percorso inoltrato e cerca la nuova voce in entrambi i registri.

**Prevenzione:** Monitora la dipendenza tramite la risposta oltre al processo frontend.

### Guasto 3 · Nome inatteso

**Sintomo:** Richiedi `wrong.lab.test` con lo stesso indirizzo e osserva 404.

**Indagine:** Confronta il nome inviato e i blocchi server letti da `nginx -T`.

**Causa:** Il server predefinito rifiuta nomi estranei al sito del lab.

**Riparazione:** Correggi il nome della richiesta in `www.lab.test`; non trasformare il predefinito in un’accettazione universale.

**Verifica:** Il nome corretto riceve il marcatore e quello errato rimane rifiutato.

**Prevenzione:** Verifica un nome valido e uno non valido quando revisioni un virtual host.

## 7 · Trappole

![Un file attraversa più di una protezione](../img/19.4-duas-portarias-do-arquivo.it.jpg)

*Indaga il diniego; conserva le protezioni del sistema.*

L’output di `nginx -T` descrive i file caricati, ma può contenere dati operativi. Esaminalo localmente e non pubblicarlo interamente senza revisione.

Una risposta 403 può derivare da permessi, politica, regola di accesso o assenza di indice. Il codice restringe l’indagine; da solo non sceglie la riparazione.

Una porta aperta sulla gestione non viene compensata da un bel nome nel DNS. L’indirizzo di ascolto limita la superficie prima della selezione HTTP.

Dopo aver corretto un diniego controlla anche un’operazione che deve restare vietata. Ripristinare il servizio non richiede di ampliare la superficie di accesso.

### Quiz · Risposte per domanda

1. Il nome seleziona il virtual host; radice e protezioni determinano la lettura del file.

2. Apache è legato soltanto al loopback, su una porta diversa dall’ingresso nginx.

3. La richiesta al percorso inoltrato, la connessione all’upstream e i registri di entrambi i servizi.

4. Quando un diniego persiste nonostante percorso, identità e modo coerenti, controlla contesto e AVC; il registro può indicare direttamente la politica.

5. L’esecuzione sulle directory permette l’attraversamento; la lettura sul file permette di ottenere il contenuto.

La risposta è completa soltanto quando spiega perché l’alternativa scartata non risolve la causa osservata. Se restano possibili due cause, aggiungi una verifica che le distingua.
