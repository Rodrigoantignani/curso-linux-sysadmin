## 2 · Por que importa

| O chamado | A resposta errada | O que acontece |
| --- | --- | --- |
| "Reiniciei o servidor e o serviço não subiu" | Iniciar de novo e fechar o chamado | Ele foi iniciado, mas nunca foi **habilitado**. No próximo reboot, o chamado volta |
| "Mudei a configuração do serviço e uma atualização desfez" | Mudar de novo no mesmo lugar | O arquivo em `/usr/lib/systemd/system` é do pacote, e o pacote o reescreve. A mudança vai num override, em `/etc`, com `systemctl edit` |
| "Desabilitei e ele voltou sozinho" | Desabilitar de novo | Outra unit puxa esse serviço como dependência, ou um socket o acorda. Para proibir de verdade, `mask` |
| "Está rodando, mas não funciona" | Reiniciar até dar certo | O motivo está escrito: `systemctl status` mostra as últimas linhas, e `journalctl -u` mostra todas |

## 3 · Modelo mental

> Todo serviço tem **dois interruptores independentes**. O primeiro é o **de agora**: `start` e `stop` ligam e desligam o processo neste momento, e o efeito some no reboot. O segundo é o **do boot**: `enable` e `disable` decidem se o serviço sobe sozinho no próximo boot, e não mexem no processo de agora. E existe uma terceira coisa, que não é interruptor: o **`mask`** tapa a tomada, e ninguém liga o serviço, nem você, nem o boot, nem outra unit.

O `systemctl status` mostra os dois interruptores em linhas separadas:

```
● relogio.service - Relogio de teste (Aula 4.2)
     Loaded: loaded (/etc/systemd/system/relogio.service; enabled; preset: disabled)
     Active: active (running) since ...
```

| Linha | Interruptor | Valores que você vai ver |
| --- | --- | --- |
| `Loaded:` | O do boot, e de onde veio o arquivo | `enabled`, `disabled`, `static` (não tem como habilitar; outra unit a puxa), `masked` |
| `Active:` | O de agora | `active (running)`, `active (exited)` (rodou e terminou bem), `inactive (dead)`, `failed`, `activating` |

Leia sempre as duas. `active` com `disabled` é o serviço que some no próximo reboot. `inactive` com `enabled` é o serviço que só vai subir no próximo boot, ou que caiu.

## 4 · O essencial

### Units

O `systemd` cuida de **units**, e o sufixo do nome diz o tipo. As que você usa todo dia:

- `.service`: um programa, como o `sshd.service`.
- `.target`: um grupo de units com nome, como o `multi-user.target`.
- `.socket`: uma porta ou um socket que acorda um serviço quando chega uma conexão.
- `.timer`: um agendamento que acorda um serviço, como o cron.
- `.mount`: uma montagem; o `systemd` gera uma para cada linha do `/etc/fstab`.

Se você não escreve o sufixo, o `systemctl` supõe `.service`: `systemctl status sshd` é o mesmo que `systemctl status sshd.service`.

### Onde moram os arquivos

| Diretório | De quem é | Prioridade |
| --- | --- | --- |
| `/etc/systemd/system/` | Seu, do administrador | Ganha de todos |
| `/run/systemd/system/` | Gerado em tempo de execução; some no reboot | Média |
| `/usr/lib/systemd/system/` | Do pacote. Na Debian 12 também aparece como `/lib/systemd/system/`, que é o mesmo lugar | A mais baixa |

A regra prática: **você nunca edita o `/usr/lib`**. O que é seu vai no `/etc`. Um arquivo com o mesmo nome no `/etc` substitui o do pacote inteiro; uma pasta `NOME.service.d/` no `/etc` com arquivos `.conf` muda só as linhas que você escrever, e o resto continua vindo do pacote. Isso é um **override**, ou drop-in.

### Os comandos

```bash
systemctl status NOME          # os dois interruptores e as últimas linhas do log
sudo systemctl start NOME      # liga agora
sudo systemctl stop NOME       # desliga agora
sudo systemctl restart NOME    # desliga e liga: o processo é novo
sudo systemctl reload NOME     # relê a configuração sem derrubar, se o serviço souber
sudo systemctl enable NOME     # sobe no boot
sudo systemctl disable NOME    # não sobe no boot
sudo systemctl enable --now NOME   # as duas coisas de uma vez
sudo systemctl disable --now NOME  # o contrário
sudo systemctl mask NOME       # ninguém liga
sudo systemctl unmask NOME     # tira o mask
systemctl is-active NOME       # só o de agora, bom para scripts
systemctl is-enabled NOME      # só o do boot
sudo systemctl daemon-reload   # depois de criar ou mudar um arquivo de unit
```

E para olhar o sistema inteiro:

```bash
systemctl list-units --type=service              # as carregadas agora
systemctl list-unit-files --type=service         # todas, com o estado do boot
systemctl --failed                               # as que falharam
systemctl cat NOME                               # o arquivo e os overrides, juntos
systemd-delta                                    # tudo o que o /etc muda em relação aos pacotes
journalctl -u NOME                               # o log só desse serviço
```

### O que o `enable` faz de verdade

O `enable` não liga nada. Ele lê a seção `[Install]` do arquivo, por exemplo `WantedBy=multi-user.target`, e cria um link em `/etc/systemd/system/multi-user.target.wants/`. No boot, o `multi-user.target` sobe tudo o que está nessa pasta. O `disable` apaga o link. E o `mask` cria um link do nome do serviço para `/dev/null`, em `/etc/systemd/system/`: como o `/etc` ganha de todos, o serviço passa a ser um arquivo vazio, que não dá para iniciar.

Uma unit sem seção `[Install]` aparece como `static`: não dá para habilitá-la, porque ela só sobe quando outra unit a puxa.

### Anatomia de um arquivo de unit

```ini
[Unit]
Description=O que aparece no status
After=network-online.target    # ordem: só começa depois deste
Wants=network-online.target    # dependência: puxa este junto

[Service]
Type=simple                    # o processo do ExecStart é o serviço
ExecStart=/usr/local/bin/programa --opcao
Restart=on-failure             # se cair com erro, sobe de novo
User=nobody                    # roda como este usuário

[Install]
WantedBy=multi-user.target     # onde o enable cria o link
```

O ponto que mais confunde: **`After=` é só ordem, e `Wants=` é só dependência.** `After=` sem `Wants=` diz "se os dois forem subir, eu vou depois", mas não faz o outro subir. `Wants=` sem `After=` puxa o outro, mas os dois sobem ao mesmo tempo. Quase sempre você quer os dois juntos. O `Requires=` é um `Wants=` mais forte: se o outro falhar, este também para.

### Override com `systemctl edit`

```bash
sudo systemctl edit NOME
```

Abre um editor com um arquivo vazio, que vira `/etc/systemd/system/NOME.service.d/override.conf`. Você escreve só o que muda, com o cabeçalho da seção, e ao salvar o `systemctl` já faz o `daemon-reload`. Falta só o `restart`. O `systemctl cat NOME` mostra o arquivo do pacote e o override, um depois do outro. Para desfazer tudo num serviço de pacote, `sudo systemctl revert NOME`.

Duas regras:

- Linhas que podem aparecer várias vezes, como `ExecStart=`, **somam**. Para trocar o `ExecStart`, você primeiro o zera com uma linha `ExecStart=` vazia, e depois escreve o novo. É a quebra da seção 6.
- O editor é o da variável `SYSTEMD_EDITOR`, ou `EDITOR`. Na Debian ele costuma abrir o `nano`: Ctrl+O, Enter e Ctrl+X salvam e saem. Para usar o `vim`: `sudo SYSTEMD_EDITOR=vim systemctl edit NOME`.

### Rocky × Debian

|  | Rocky | Debian |
| --- | --- | --- |
| Arquivos dos pacotes | `/usr/lib/systemd/system/` | `/lib/systemd/system/`, o mesmo que `/usr/lib/systemd/system/` |
| Nome do serviço do SSH | `sshd` | `ssh` |
| Serviço novo, recém-instalado | Fica parado e desabilitado: você faz o `enable --now` | Em geral já sobe e fica habilitado na instalação |
| Editor do `systemctl edit` | Costuma ser o `vi` | Costuma ser o `nano` |

A terceira linha pega muita gente: na Rocky, `dnf install` não liga nada. Na prova da RHCSA, um serviço instalado e não habilitado é ponto perdido no reboot que o corretor faz.

### O que cai na prova

Na RHCSA: iniciar, parar e conferir serviços, e deixar habilitados no boot. O corretor reinicia a sua máquina antes de corrigir, então tudo o que você só iniciou, sem habilitar, conta como não feito. Na LPIC-1 101.3: os comandos do `systemctl`, o que é uma unit e um target, e onde ficam os arquivos.

### Passo 2 · Criar um serviço

```bash
sudoedit /etc/systemd/system/relogio.service
```

```ini
[Unit]
Description=Relogio de teste (Aula 4.2)

[Service]
Type=simple
Environment=MSG=tique
ExecStart=/bin/bash -c 'while true; do echo $MSG; sleep 10; done'

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
systemctl status relogio
sudo systemctl start relogio
systemctl status relogio
journalctl -u relogio -f
```

O primeiro `status` mostra `inactive (dead)` e `disabled`. Depois do `start`, `active (running)`, ainda `disabled`. O `journalctl -f` mostra um `tique` a cada 10 segundos. Saia com Ctrl+C: isso fecha o `journalctl`, não o serviço.

**Decida 1.** O `relogio` está rodando e está `disabled`. Marque: depois de um reboot, ele vai estar

- a) rodando
- b) parado
- c) mascarado

```bash
sudo systemctl reboot
```

Depois de entrar de novo:

```bash
systemctl status relogio
```

| Se você marcou | Resultado | Por quê |
| --- | --- | --- |
| a | Errou | O `start` só mexe no interruptor de agora. Ninguém pediu para ele subir no boot |
| b | Acertou | `inactive (dead)`, `disabled`. É o chamado da primeira linha da seção 2 |
| c | Errou | Mascarar só acontece se alguém pedir com `mask` |

**Para fixar:** `start` vale até o reboot; `enable` vale a partir do próximo boot. Na prova, e na vida, faça os dois: `enable --now`.

### Passo 3 · Habilitar, ver o link, e mascarar

```bash
sudo systemctl enable --now relogio
ls -l /etc/systemd/system/multi-user.target.wants/ | grep relogio
systemctl list-dependencies --reverse relogio
```

O `enable` respondeu `Created symlink ...`, e o `ls` mostra o link para o seu arquivo. O `list-dependencies --reverse` mostra quem puxa o `relogio`: o `multi-user.target`.

**Decida 2.** Marque: `sudo systemctl mask relogio` vai

- a) mascarar, e o `start` passa a recusar
- b) dar erro
- c) apagar o arquivo `relogio.service`

```bash
sudo systemctl mask relogio
```

| Se você marcou | Resultado | Por quê |
| --- | --- | --- |
| a | Errou | Seria assim com um serviço de pacote |
| b | Acertou | Algo como `Failed to mask unit: File /etc/systemd/system/relogio.service already exists`. O `mask` cria um link com o nome do serviço **no `/etc`**, e o seu arquivo já está lá com esse nome |
| c | Errou | O `systemctl` nunca apaga o seu arquivo para mascarar |

**Para fixar:** o `mask` serve para serviços de pacote, os que moram no `/usr/lib`. Para um serviço seu, no `/etc`, desabilitar e parar já basta.

Agora mascare um serviço de pacote que existe nas duas distros e fica sempre desligado: o `debug-shell.service`.

> **Não inicie o `debug-shell`.** Ele abre um shell de root, sem senha, no terminal 9 da console. Ele existe para depurar o boot, e por isso mesmo é um bom candidato a ficar mascarado.

```bash
sudo systemctl mask debug-shell
ls -l /etc/systemd/system/debug-shell.service
systemctl is-enabled debug-shell
sudo systemctl start debug-shell
sudo systemctl unmask debug-shell
systemctl is-enabled debug-shell
```

O `ls` mostra o link para `/dev/null`, o `is-enabled` responde `masked`, e o `start` recusa com `Unit debug-shell.service is masked`. Depois do `unmask`, ele volta a `disabled`. Era isso que o `mask` fazia, e por isso o `start` recusou sem nunca rodar o serviço.

### Passo 4 · Mudar o serviço com um override

```bash
sudo systemctl edit relogio
```

No editor, escreva só isto, no espaço indicado pelos comentários do arquivo:

```ini
[Service]
Environment=MSG=taque
```

Salve e saia. Depois:

```bash
ls /etc/systemd/system/relogio.service.d/
systemctl cat relogio
sudo systemctl restart relogio
journalctl -u relogio -n 5
systemd-delta
```

O `cat` mostra os dois arquivos, o original e o `override.conf`. Depois do `restart`, o log passa a dizer `taque`: a segunda linha `Environment=MSG=` ganhou da primeira. E o `systemd-delta` agora lista o seu override, marcado como `[EXTENDED]`.

## 6 · Quebre e conserte

**A quebra:** trocar o comando do serviço pelo override, do jeito que parece óbvio.

```bash
sudo systemctl edit relogio
```

Deixe o override assim:

```ini
[Service]
Environment=MSG=taque
ExecStart=/bin/bash -c 'while true; do echo novo; sleep 5; done'
```

```bash
sudo systemctl restart relogio
```

**O diagnóstico.** O `restart` recusa, com algo como `Unit relogio.service has a bad unit file setting`. Procure o motivo:

```bash
systemctl status relogio
journalctl -u relogio -n 20
```

O motivo está escrito: `Service has more than one ExecStart= setting, which is only allowed for Type=oneshot services. Refusing.` O `ExecStart` do override **somou** com o do arquivo original, e um serviço `simple` só aceita um.

**O conserto.** Abra o override de novo e zere o `ExecStart` antes de escrever o novo:

```ini
[Service]
Environment=MSG=taque
ExecStart=
ExecStart=/bin/bash -c 'while true; do echo novo; sleep 5; done'
```

```bash
sudo systemctl restart relogio
journalctl -u relogio -n 5
```

Agora aparece `novo` a cada 5 segundos.

**A lição.** Quando um serviço não sobe, não adivinhe: o `systemctl status` e o `journalctl -u` quase sempre dizem a causa com todas as letras. E num override, as linhas que podem se repetir somam; para trocar uma delas, você zera primeiro.

## 7 · Armadilhas

- **`start` sem `enable`.** Funciona até o próximo reboot. Na RHCSA, o corretor reinicia a máquina antes de corrigir.
- **Editar o arquivo em `/usr/lib/systemd/system/`.** A próxima atualização do pacote desfaz. Use `systemctl edit`.
- **Esquecer o `daemon-reload` depois de editar um arquivo de unit à mão.** O `systemd` continua usando a versão antiga e avisa. O `systemctl edit` já faz o reload sozinho.
- **Trocar o `ExecStart=` num override sem zerar antes.** É a quebra da seção 6.
- **`After=` achando que puxa o outro serviço.** `After=` é só ordem; quem puxa é `Wants=` ou `Requires=`.
- **`disable` achando que proibiu.** Outra unit, ou um socket, ainda pode ligar o serviço. Para proibir, `mask`.
- **Reiniciar o SSH remoto com uma configuração quebrada.** As sessões abertas sobrevivem, mas nenhuma nova entra. Antes do `restart`, teste com `sudo sshd -t`, que não responde nada quando está tudo certo.
- **`sshd` na Debian.** Lá o serviço é `ssh`.

### Flashcards

- `start` e `enable`: qual vale no boot? → `enable`.
- Onde vai o que é seu? → `/etc/systemd/system/`.
- O que o `mask` cria? → Um link do nome do serviço para `/dev/null`, no `/etc/systemd/system/`.
- `static` quer dizer? → Sem seção `[Install]`: não dá para habilitar, outra unit a puxa.
- `After=` puxa o outro serviço? → Não, só define a ordem.
- Como trocar o `ExecStart` num override? → `ExecStart=` vazio, depois o novo.
- O serviço não sobe: onde está o motivo? → `systemctl status` e `journalctl -u`.

## 12 · Aprofundar quando quiser

- **Os outros `Type=`**: `forking`, `oneshot` com `RemainAfterExit=`, `notify`, e quando cada um é o certo.
- **`Restart=` e os limites**: `RestartSec=`, `StartLimitBurst=`, e por que um serviço que cai em loop acaba parado.
- **Sockets e timers**: como um `.socket` acorda um serviço, e os `.timer` como alternativa ao cron. Os timers voltam no módulo de agendamento.
- **Units de template**: o `@` em nomes como `getty@tty1.service`.
- **Units de usuário**: `systemctl --user`, sem root.
- **Presets**: `systemctl preset`, e por que a Rocky deixa os serviços novos desligados.
- **Endurecer um serviço**: `ProtectSystem=`, `PrivateTmp=` e `systemd-analyze security`.

## Gabarito comentado

### Aquecimento

1. **Parar** desliga agora, e no próximo boot o serviço pode voltar. **Desabilitar** tira o serviço do boot, mas não desliga o que está rodando. São os dois interruptores.
2. O `/usr/lib/systemd/system/` é do pacote. A atualização trouxe o arquivo novo e sobrescreveu o seu. A mudança vai num override no `/etc`, com `systemctl edit`.
3. Outra unit que depende dele, ou um `.socket` que o acorda quando chega uma conexão. O `disable` só tira o link do boot. Para proibir de verdade, `mask`.

### Quiz

1. Ele não sobe no próximo boot. `sudo systemctl enable NOME`; ou, se estivesse parado, `enable --now`.
2. Um link em `/etc/systemd/system/multi-user.target.wants/`, com o nome do serviço, apontando para o arquivo da unit.
3. Num override: `sudo systemctl edit NOME`, com `[Service]` e `User=OUTRO`, e depois `restart`. O arquivo vai para `/etc/systemd/system/NOME.service.d/override.conf`, que a atualização não toca.
4. `disable` tira o serviço do boot, mas você, outra unit ou um socket ainda podem ligá-lo. `mask` aponta o serviço para `/dev/null`, e ninguém consegue ligá-lo até o `unmask`.
5. `After=` só define a ordem: se os dois subirem, este vai depois. Para puxar o PostgreSQL junto, falta `Wants=postgresql.service` ou `Requires=postgresql.service`, ou habilitar o PostgreSQL.
6. `systemctl enable --now NOME`.
