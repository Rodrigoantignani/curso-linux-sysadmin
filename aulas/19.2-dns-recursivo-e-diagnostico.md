## 1 · Aquecimento

1. Qual diferença existe entre AA e RA em uma resposta DNS?

2. O TTL de uma resposta em cache precisa acompanhar imediatamente uma mudança na origem?

3. Qual servidor você consultou no último diagnóstico DNS?

Desenhe cliente, resolvedor e autoridade.

Acrescente o caminho de saída da VM 204 pela gestão, sem transformá-la em roteador dos clientes.

## 2 · Por que importa

O serviço responde pela zona local, mas o cliente também pergunta por nomes externos.

Isso exige um papel adicional: buscar uma resposta em nome do cliente e manter um cache.

Uma consulta externa pode falhar por rota, firewall, encaminhador, DNSSEC, relógio ou delegação.

Reiniciar o DNS sem separar essas causas perde evidências.

### Ponte Windows

Limpar o cache de um cliente não limpa o cache do servidor.

Identifique a camada antes de pedir uma limpeza ou anunciar que o problema acabou.

## 3 · Modelo mental

![Autoridade e recursão são papéis diferentes](../img/19.2-autoridade-e-recursao.jpg)

*Responder pela própria zona não autoriza atender recursão para todos.*

Autoridade conhece a própria zona; recursor busca respostas de outras zonas.

O mesmo processo BIND pode exercer os dois papéis com controles distintos.

RD é o pedido de recursão enviado pelo cliente.

RA anuncia a disponibilidade de recursão; AA caracteriza uma resposta autoritativa.

Esses sinais respondem a perguntas diferentes.

![O cache tem prazo](../img/19.2-tempo-de-cache.jpg)

*Um valor em cache pode continuar válido depois da mudança na origem.*

TTL é o prazo de conservação de um registro em cache.

Não mede latência, não garante atualização instantânea e não substitui o serial da zona.

### Rocky × Debian

BIND permanece na VM 204 Debian; você pode repetir as consultas explícitas da VM 201 Rocky.

Compare as respostas do mesmo servidor antes de comparar os resolvedores locais das distribuições.

## 4 · O essencial

| Evidência | Pergunta respondida |
| --- | --- |
| SERVER | Quem recebeu esta consulta? |
| AA | A resposta vem de autoridade para a pergunta? |
| RA | O servidor anuncia recursão disponível? |
| NXDOMAIN | O nome consultado não existe? |
| SERVFAIL | O servidor não conseguiu concluir? |
| timeout | Houve resposta dentro do prazo? |
| TTL | Por quanto tempo o registro pode permanecer em cache? |

Não copie um resolvedor público como encaminhador por hábito.

Use somente endereços reais autorizados da gestão e teste o alcance a partir da VM 204.

Um encaminhador evita consultas iterativas diretas quando a rede restringe a saída.

Se ele falha, a política escolhida define se existe outra tentativa.

### Decida 1

O A local funciona e nomes externos dão SERVFAIL.

Qual teste reduz melhor o problema?

A. Trocar o endereço de gestão da VM 202.

B. Consultar diretamente o encaminhador real a partir da VM 204.

C. Desativar DNSSEC e o firewall ao mesmo tempo.

## 5 · Lab guiado

### Passo 1 · Registrar a base e a saída autorizada

**Palpite:** O cliente isolado precisa de gateway para perguntar à VM 204?

No host, preserve o estado inicial com `qm snapshot 204 m19a2-inicio`.

Na VM 204, registre as interfaces, a rota de gestão e a configuração atual antes de qualquer mudança.

```bash
ip -br address
ip -4 route
cat /etc/resolv.conf
sudo named-checkconf
dig @192.0.2.204 app.lab.test A +norecurse
sudo test ! -e /etc/bind/named.conf.options.m19a2-before || exit 1
sudo cp -a /etc/bind/named.conf.options /etc/bind/named.conf.options.m19a2-before
```

Leia o DNS real configurado na gestão.

Se `resolv.conf` mostrar um stub de loopback, identifique o servidor a montante pelo gerenciador efetivamente instalado e pela documentação da rede.

Não use o próprio BIND como encaminhador de si mesmo.

```bash
read -r -p "IPv4 do DNS real autorizado da gestao: " UPSTREAM_DNS
python3 - "$UPSTREAM_DNS" <<'PY'
import ipaddress,sys
a=ipaddress.IPv4Address(sys.argv[1])
assert not (a.is_loopback or a.is_unspecified or a.is_multicast)
assert a not in ipaddress.IPv4Network("192.0.2.0/24")
PY
test "$?" -eq 0 || exit 1
ip -4 route get "$UPSTREAM_DNS"
dig @"$UPSTREAM_DNS" www.debian.org A +time=3 +tries=1
dig @"$UPSTREAM_DNS" www.debian.org A +tcp +time=3 +tries=1
```

**Saída esperada:** A VM 204 alcança o DNS autorizado pela gestão usando UDP e TCP. O cliente continua sem gateway na placa isolada.

**Verifique:** Pare se o DNS autorizado não responder. Corrija a saída da VM 204 antes de habilitar o serviço recursivo.

### Passo 2 · Ativar recursão somente para a ACL

**Palpite:** Limitar quem faz consultas também exige limitar o acesso ao cache?

Esta variante usa `forward only` para tornar a dependência do encaminhador explícita.

Não haverá tentativa iterativa direta se ele falhar.

```bash
[[ "$UPSTREAM_DNS" =~ ^[0-9.]+$ ]] || exit 1
sudo tee /etc/bind/named.conf.options >/dev/null <<EOF
acl m19_trusted { 127.0.0.1; 192.0.2.0/24; };
options {
    directory "/var/cache/bind";
    listen-on { 127.0.0.1; 192.0.2.204; };
    listen-on-v6 { none; };
    allow-query { m19_trusted; };
    allow-transfer { none; };
    recursion yes;
    allow-recursion { m19_trusted; };
    allow-query-cache { m19_trusted; };
    forward only;
    forwarders { $UPSTREAM_DNS; };
    dnssec-validation auto;
};
EOF
sudo named-checkconf && sudo rndc reconfig
sudo systemctl is-active named
sudo ss -lntup | grep ":53"
sudo journalctl -u named -b --no-pager -n 30
```

Se a validação falhar, restaure o arquivo anterior e valide antes de recarregar.

Não deixe uma tentativa inválida como configuração de boot.

**Saída esperada:** Autoridade local preservada, recursão e cache limitados à ACL; BIND continua fora do endereço de gestão.

**Verifique:** Leia as três diretivas de ACL. Um simples `recursion yes` não é uma política completa para um servidor acessível por clientes.

### Passo 3 · Separar resposta local e externa

**Palpite:** Um nome externo devolvido pelo recursor deve trazer AA?

Na VM 202, mantenha o perfil isolado `m19-isolada` e use o endereço explícito.

Não altere o resolvedor global nem o perfil de gestão.

```bash
dig @192.0.2.204 app.lab.test A +norecurse
dig @192.0.2.204 www.debian.org A
dig @192.0.2.204 lab.test MX +norecurse
dig @192.0.2.204 -x 192.0.2.204 +norecurse
```

**Saída esperada:** A zona local conserva AA; a resposta externa bem-sucedida vem com recursão disponível e normalmente sem AA. Leia o status e a seção SERVER.

**Verifique:** Se houver SERVFAIL, compare com a consulta direta ao encaminhador na VM 204. Se houver timeout, confira primeiro caminho, sockets e firewall.

Um NXDOMAIN externo pode ser uma resposta negativa válida.

Não trate todo resultado sem endereço como falha de transporte.

### Passo 4 · Observar cache sem fabricar tempos

**Palpite:** A segunda consulta sempre será mais rápida, com TTL exatamente menor?

```bash
date -Is
dig @192.0.2.204 www.debian.org A +noall +answer +stats
sleep 2
date -Is
dig @192.0.2.204 www.debian.org A +noall +answer +stats
```

Registre RRset, TTL, servidor e tempo observado.

Em um cache estável, o TTL restante tende a diminuir; prefetch, expiração, respostas variáveis e cache do encaminhador podem mudar a observação.

Consultar a própria zona autoritativa não é um experimento de TTL de cache recursivo.

O valor mostrado pode ser o TTL original do registro local.

```bash
sudo rndc flushname www.debian.org
dig @127.0.0.1 www.debian.org A +noall +answer +stats
sudo rndc status
```

O comando de limpeza é feito na VM 204 e afeta somente esse nome no BIND local.

Não limpa o encaminhador nem o cliente.

**Saída esperada:** Você obtém evidências comparáveis, sem um valor de latência prometido. O cache a montante pode continuar respondendo após a limpeza local.

**Verifique:** Anote explicitamente o que o teste não prova: ele não demonstra que todas as camadas foram esvaziadas.

### Passo 5 · Seguir delegações pelo caminho certo

**Palpite:** O `+trace` usa necessariamente o mesmo caminho do encaminhador configurado no BIND?

![Siga o caminho da pergunta](../img/19.2-caminho-da-pergunta.jpg)

*Compare servidor consultado, tipo de resposta e caminho antes de corrigir.*

```bash
dig +trace debian.org A
dig @192.0.2.204 debian.org A
ip -4 route
timedatectl status
```

Execute o trace na VM 204, cuja gestão possui a saída autorizada.

Ele faz consultas iterativas próprias, após a descoberta inicial; não reproduz a cadeia de encaminhamento do serviço.

Uma rede que só permite DNS ao encaminhador pode bloquear o trace e ainda permitir o recursor configurado.

Registre essa limitação em vez de mudar firewall para obter um desenho bonito.

Compare delegação, servidor consultado e resultado final.

Para SERVFAIL com DNSSEC, examine também hora e logs; não desligue a validação sem evidência da causa.

**Saída esperada:** Trace e consulta recursiva são experimentos diferentes; um pode funcionar quando o outro é bloqueado pela política de saída.

**Verifique:** Desenhe os dois caminhos e identifique qual processo abre as consultas externas em cada caso.

### Decida 2

O trace falha, mas a consulta via BIND e encaminhador funciona.

Qual conclusão cabe?

A. Os caminhos têm permissões diferentes; ainda não há prova de falha do BIND.

B. O cliente deve receber o gateway da VM 204.

C. Todo DNS externo está quebrado.

### Passo 6 · Conferir limites e persistência

**Palpite:** A recursão para o lab exige escutar no endereço de gestão?

Na VM 204, leia a configuração efetiva e os sockets.

Não abra temporariamente o serviço na gestão para produzir um teste negativo.

```bash
sudo named-checkconf -p | grep -A 6 -E "allow-query|allow-recursion|allow-query-cache|listen-on"
sudo ss -lntup | grep ":53"
sudo sysctl net.ipv4.ip_forward
ip -4 route
```

A VM 204 deve continuar sem encaminhamento de pacotes entre placas.

Recursão DNS é uma conversa feita pelo processo servidor, não NAT do tráfego dos clientes.

**Reboot de conferência:** Com console disponível, reinicie somente 204. Reabra a gestão e repita A local, nome externo e sockets.

```bash
sudo systemctl reboot
```

Depois do boot na VM 204 e da consulta externa na VM 202:

```bash
sudo systemctl is-active named
dig @192.0.2.204 app.lab.test A +norecurse
dig @192.0.2.204 www.debian.org A
```

**Saída esperada:** Ambos os papéis persistem, com escopo restrito. O caminho real da gestão continua documentado no diário.

**Verifique:** No host, faça `qm snapshot 204 m19a2-fim` após as verificações. Preserve a configuração para DHCP, correio e web.

## 6 · Quebre e conserte

### Quebra 1 · Encaminhador inalcançável

**Sintoma:** A local responde; consulta externa falha.

**Investigação:** Na VM 204, compare `ip -4 route` e consultas diretas ao encaminhador com UDP e TCP.

**Causa:** A saída autorizada ou o DNS a montante falha; `forward only` não tenta outra rota de resolução.

**Conserto:** Restaure a conectividade autorizada; mantenha as ACLs e a validação.

**Verifique:** Teste primeiro o encaminhador, depois BIND, por último o cliente.

**Prevenção:** Registre qual dependência existe fora da zona local.

### Quebra 2 · Cliente consultando outro DNS

**Sintoma:** O navegador falha, mas `dig @192.0.2.204 app.lab.test A` funciona.

**Investigação:** Compare o servidor explícito, a resolução do sistema e eventuais configurações próprias da aplicação.

**Causa:** A aplicação ou o sistema usa outro caminho de resolução.

**Conserto:** Corrija somente a camada identificada em uma mudança autorizada; não altere a gestão no exercício.

**Verifique:** Repita exatamente a consulta que falhava, pelo mesmo caminho.

**Prevenção:** Sempre anote o servidor e a ferramenta usados.

### Quebra 3 · Cache não acompanha a edição

**Sintoma:** Outro resolvedor ainda devolve um valor antigo após a mudança da autoridade.

**Investigação:** Compare autoridade, serial, TTL restante e o servidor que mantém a resposta.

**Causa:** Uma cópia válida permanece em cache até seu prazo, ou há outra camada.

**Conserto:** Confirme a origem e aguarde o TTL observado; limpe somente o cache autorizado e identificado.

**Verifique:** A consulta posterior converge para a origem sem quebrar a gestão.

**Prevenção:** Planeje TTL antes de migrações e guarde evidência da versão anterior.
