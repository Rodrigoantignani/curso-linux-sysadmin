# Aula 12.4 · SELinux: portas e booleanos

Na aula anterior, você corrigiu o tipo de um arquivo sem afrouxar suas permissões. Agora vai separar duas outras decisões: um serviço pode escutar nessa porta? Ele pode abrir uma conexão de saída? Na Debian, um perfil nomeado de AppArmor mostra outra forma de confinar um processo escolhido.

> **Núcleo desta aula:** contexto de arquivo, tipo de porta e booleano de saída resolvem problemas diferentes. Leia a negativa e confirme o confinamento real antes de liberar. O resto é aprofundamento.

## 1 · Aquecimento

Responda sem consultar. As respostas ficam no fim.

1. Por que um arquivo legível por DAC ainda pode ser recusado pelo processo web?
2. O que registrar uma regra com `semanage fcontext` faz sem `restorecon`?

## 2 · Por que importa

Você muda a porta do nginx e ele para de iniciar. O arquivo de configuração passa no teste, a porta está livre e o firewall não participa do bind local. O evento de auditoria revela uma operação de bind negada. Mudar o contexto do HTML não corrigiria essa causa.

Depois, o serviço inicia e entrega uma resposta local, mas o proxy retorna erro. Agora a negativa envolve a conexão de saída até o backend. O serviço tem duas necessidades distintas, portanto duas evidências distintas.

| Operação | Controle que você investiga |
| --- | --- |
| Ler conteúdo | DAC e tipo do arquivo |
| Escutar TCP | Socket livre, domínio e tipo da porta |
| Conectar a backend | Destino disponível e política de saída |

## 3 · Modelo mental

No prédio do curso, o crachá do processo não abre qualquer sala nem permite qualquer ligação externa. O tipo do arquivo identifica o recurso; o tipo da porta identifica um uso da rede; o booleano habilita uma capacidade prevista pela política.

```text
httpd_t -> arquivo httpd_sys_content_t -> leitura
httpd_t -> porta http_port_t          -> bind
httpd_t -> destino de rede            -> política de saída
```

![Três autorizações diferentes](../img/12.4-arquivo-porta-e-saida.jpg)

*Liberar a porta não autoriza qualquer arquivo ou conexão de saída.*

### Ponte Windows

| Conceito conhecido | O que comparar no Linux |
| --- | --- |
| Conta do serviço | Domínio SELinux ou perfil AppArmor do processo |
| Permissão do arquivo | DAC mais a política MAC ativa |
| Porta liberada no firewall | Não substitui autorização MAC para bind |
| Evento de acesso negado | Operação, origem e alvo do evento |

## 4 · O essencial

### Portas têm tipos

`semanage port -l` mostra associações da política. `-C` limita a listagem às personalizações locais. Antes de adicionar uma porta, examine também os intervalos que a contêm; procurar apenas o número com `grep` pode perder uma faixa.

`-a` adiciona uma associação; `-m` modifica uma existente. Não troque o tipo de uma porta de outro serviço para fazer um exemplo funcionar. Neste lab, a porta precisa estar sem associação específica de serviço; um tipo genérico de portas não reservadas é a condição normal.

### Booleano é uma capacidade da política

`getsebool` mostra o valor ativo. `setsebool` altera esse valor; `-P` também o persiste para os próximos boots. Registre o estado inicial antes de mudar. A capacidade `httpd_can_network_connect` permite conexões de rede de saída ao domínio web, portanto exige uma necessidade justificada.

Ela não inicia backend, não cria uma escuta e não abre o firewall. O efeito só aparece quando o processo está no domínio ao qual a regra se aplica.

### Leia o AVC antes da correção

No evento, `scontext` identifica o contexto de origem; `tcontext`, o alvo. A classe e a operação negada mostram o tipo de acesso tentado. Cruze horário, processo e porta com o teste que acabou de executar.

![Leia a negativa antes de liberar](../img/12.4-ler-a-negativa.jpg)

*Cruze o evento com o processo, o alvo e a operação.*

Não transforme todo AVC em um módulo automático de permissão. Primeiro confirme configuração, contexto, porta e capacidade já prevista pela política.

### AppArmor: perfil realmente carregado

AppArmor estar ativo não significa que qualquer processo esteja confinado. O lab usa um perfil nomeado, sem associação automática ao executável: apenas a execução pedida com `aa-exec -p` entra nele. O mesmo leitor fora desse perfil continua com seu comportamento normal.

![Duas formas de confinar](../img/12.4-rotulos-e-perfis.jpg)

*Confira qual mecanismo e qual política estão ativos.*

## 5 · Lab guiado

Use somente as VMs do curso e preserve noVNC e SSH. A Rocky precisa estar em enforcing, sem outro serviço no domínio web; nginx original deve estar inativo. A Debian precisa ter AppArmor ativo no kernel e no boot antes do exercício. Não habilite um mecanismo ausente no meio deste roteiro.

### Passo 1 · Proteger e registrar

**Palpite:** um programa executado como root fica automaticamente fora da política MAC?

No host Proxmox:

```bash
qm snapshot 201 m12a4-inicio
qm snapshot 202 m12a4-inicio
```

Nas duas VMs, confirme que a pasta está ausente antes de criar. Na Rocky, instale somente os pacotes que faltarem ao preparo da 12.3.

```bash
test ! -e "$HOME/m12a4"
mkdir -m 700 "$HOME/m12a4"
```

Na Rocky:

```bash
sudo dnf install -y nginx policycoreutils-python-utils audit curl python3
getenforce
systemctl is-active nginx
systemctl is-active auditd
ps -eZ | grep httpd_t
sudo ss -lntp 'sport = :18094 or sport = :18095'
getsebool httpd_can_network_connect | tee "$HOME/m12a4/boolean.inicio"
sudo semanage boolean -l | grep '^httpd_can_network_connect ' | tee "$HOME/m12a4/boolean.persistente.inicio"
sudo semanage port -l -n > "$HOME/m12a4/ports.inicio"
sudo semanage port -l -C > "$HOME/m12a4/ports-locais.inicio"
```

Na Debian, instale utilitários se necessário, sem iniciar um mecanismo até então desativado:

```bash
sudo apt install -y apparmor apparmor-utils
sudo aa-status
systemctl is-active apparmor
systemctl is-enabled apparmor
readlink -f /bin/cat
sudo test ! -e /etc/apparmor.d/m12a4-leitor
```

**Saída esperada:** Rocky em enforcing, auditoria ativa, nginx original inativo, sem processo `httpd_t` nem escuta nas portas reservadas. Na Debian, AppArmor ativo e habilitado, com `cat` resolvendo para `/usr/bin/cat`; o perfil exclusivo ainda não existe.

**Verifique:** o valor ativo e o persistente do booleano precisam coincidir neste lab. Guarde esse estado para a restauração. Confirme também que não existem `/etc/nginx/m12a4.conf`, `/etc/systemd/system/m12a4-nginx.service` nem uma regra local de contexto para a árvore de runtime do exercício.

### Passo 2 · Identificar a porta e preparar a instância

**Palpite:** uma porta sem processo em escuta pode ter um tipo SELinux de outro serviço?

Somente na Rocky, o leitor abaixo também examina intervalos da tabela.

```bash
python3 - <<'PY'
from pathlib import Path
rows = Path.home().joinpath('m12a4/ports.inicio').read_text().splitlines()
for port in (18094, 18095):
    for row in rows:
        fields = row.split()
        if len(fields) < 3 or fields[1] != 'tcp':
            continue
        for item in ''.join(fields[2:]).split(','):
            lo, _, hi = item.partition('-')
            if int(lo) <= port <= int(hi or lo):
                print(port, fields[0], item)
PY
```

Continue apenas se as duas portas tiverem somente tipos genéricos, sem associação específica a serviço e sem personalização local. `18094` será a porta web; `18095`, o backend. Não use `-m` para tomar uma porta já atribuída.

Crie a configuração e a unidade exclusivas. O runtime recebe uma regra própria; a equivalência SELinux faz `/run` corresponder a `/var/run`.

```bash
sudo semanage fcontext -a -t httpd_var_run_t '/var/run/nginx-m12a4(/.*)?'
sudo tee /etc/nginx/m12a4.conf > /dev/null <<'EOF'
pid /run/nginx-m12a4/nginx.pid;
error_log /var/log/nginx/m12a4-error.log notice;
events {}
http {
    access_log off;
    server {
        listen 127.0.0.1:18094;
        location = /health { return 200 'POLICY ok\n'; }
        location / { proxy_pass http://127.0.0.1:18095; }
    }
}
EOF
sudo restorecon /etc/nginx/m12a4.conf
sudo tee /etc/systemd/system/m12a4-nginx.service > /dev/null <<'EOF'
[Unit]
Description=M12A4 nginx lab
After=network.target
[Service]
Type=simple
RuntimeDirectory=nginx-m12a4
ExecStartPre=/usr/sbin/restorecon -R /run/nginx-m12a4
ExecStartPre=/usr/sbin/nginx -t -c /etc/nginx/m12a4.conf
ExecStart=/usr/sbin/nginx -c /etc/nginx/m12a4.conf -g "daemon off;"
[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl start m12a4-nginx
sudo journalctl -u m12a4-nginx -n 15 --no-pager
sudo ausearch -m AVC -ts recent -c nginx -i
```

**Saída esperada:** a unidade falha ao tentar escutar a porta ainda não autorizada. O AVC do teste aponta uma negativa de bind; não copie um evento antigo como evidência desta tentativa.

**Verifique:** confirme a porta e o domínio no evento. Uma falha de sintaxe, arquivo ou runtime exige corrigir essa causa antes de atribuir o problema à porta.

### Decida 1

O AVC envolve bind na porta de exercício. Qual mudança corresponde à necessidade?

| Opção | Ação |
| --- | --- |
| A | Mudar o contexto do HTML |
| B | Adicionar a porta própria ao tipo de porta web |
| C | Desativar enforcing |

Escolha B. O evento descreve uma operação de rede, não leitura de conteúdo.

### Passo 3 · Autorizar bind e comprovar o domínio

**Palpite:** adicionar o tipo da porta também cria uma regra de firewall?

Na Rocky, adicione somente a associação previamente verificada.

```bash
sudo semanage port -a -t http_port_t -p tcp 18094
sudo systemctl reset-failed m12a4-nginx
sudo systemctl start m12a4-nginx
ps -eZ | grep nginx
sudo ss -lntp 'sport = :18094'
curl --noproxy '*' --max-time 4 -fsS http://127.0.0.1:18094/health
sudo semanage port -l -C
sudo systemctl enable m12a4-nginx
```

**Saída esperada:** nginx em `httpd_t`, escuta de loopback e resposta `POLICY ok`. A associação de porta é persistente e a unidade própria fica habilitada. Nenhuma porta externa foi aberta.

**Verifique:** se o processo não estiver em `httpd_t`, pare: um sucesso sem o domínio correto não demonstra a política esperada.

### Passo 4 · Justificar uma conexão de saída

**Palpite:** o processo poder escutar em `18094` já permite conectar ao backend em `18095`?

Na Rocky, abra o backend no terminal A como `student`. Ele não é um serviço persistente.

```bash
mkdir "$HOME/m12a4/www"
printf 'BACKEND ok\n' > "$HOME/m12a4/www/index.html"
python3 -m http.server 18095 --bind 127.0.0.1 --directory "$HOME/m12a4/www"
```

No terminal B, confirme o backend diretamente e plante o estado fechado apenas no lab sem outros processos web.

```bash
curl --noproxy '*' --max-time 4 -fsS http://127.0.0.1:18095/
sudo setsebool httpd_can_network_connect off
curl --noproxy '*' --max-time 4 -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18094/
sudo ausearch -m AVC -ts recent -c nginx -i
sudo setsebool -P httpd_can_network_connect on
getsebool httpd_can_network_connect
curl --noproxy '*' --max-time 4 -fsS http://127.0.0.1:18094/
```

**Saída esperada:** backend direto entrega `BACKEND ok`; com a capacidade fechada, o proxy falha e o evento correlato mostra conexão negada. Depois da autorização persistente, o mesmo proxy entrega `BACKEND ok`.

**Verifique:** procure a operação de conexão e o destino do teste. Se a política já permitir essa conexão por outra regra, registre isso; não invente uma negativa e não acrescente permissões sem necessidade.

### Decida 2

Após habilitar o booleano, o proxy ainda falha. Qual teste separa política de backend parado?

| Opção | Ação |
| --- | --- |
| A | Abrir a porta no firewall externo |
| B | Testar diretamente o backend e conferir socket e AVC recente |
| C | Autorizar todos os AVCs automaticamente |

Escolha B. A autorização não inicia o processo que deveria receber a conexão.

### Passo 5 · Confinar um leitor na Debian

**Palpite:** dois arquivos com os mesmos modos DAC podem ter resultados diferentes dentro de um perfil AppArmor?

Somente na Debian, confirme a ausência da árvore antes de criar. O perfil não possui uma associação automática a todos os usos de `cat`.

```bash
sudo test ! -e /srv/m12a4-aa
sudo install -d -m 755 /srv/m12a4-aa
printf 'PUBLIC ok\n' | sudo tee /srv/m12a4-aa/public.txt > /dev/null
printf 'PRIVATE lab\n' | sudo tee /srv/m12a4-aa/private.txt > /dev/null
sudo chmod 644 /srv/m12a4-aa/public.txt /srv/m12a4-aa/private.txt
sudo tee /etc/apparmor.d/m12a4-leitor > /dev/null <<'EOF'
#include <tunables/global>
profile m12a4-leitor {
    #include <abstractions/base>
    #include <abstractions/consoles>
    /usr/bin/cat mrix,
    /srv/m12a4-aa/public.txt r,
}
EOF
sudo apparmor_parser -Q -T /etc/apparmor.d/m12a4-leitor
sudo apparmor_parser -a -T /etc/apparmor.d/m12a4-leitor
sudo aa-status
cat /srv/m12a4-aa/private.txt
sudo aa-exec -p m12a4-leitor -- /usr/bin/cat /srv/m12a4-aa/public.txt
sudo aa-exec -p m12a4-leitor -- /usr/bin/cat /srv/m12a4-aa/private.txt
```

**Saída esperada:** o perfil compila e entra em modo de aplicação. Fora dele, o arquivo privado do exercício é legível; dentro dele, somente o público é autorizado entre esses dois arquivos. O último comando recebe negativa mesmo executado como root.

**Verifique:** `aa-status` precisa listar `m12a4-leitor` em enforce. A abstração base permite o carregamento normal do programa e bibliotecas; a de consoles mantém a saída no terminal da sessão; a regra de conteúdo permite apenas o caminho público do exercício. Não amplie o perfil para toda a árvore para esconder uma falha.

### Passo 6 · Conferir persistência

**Palpite:** o booleano persistente também fará o backend Python voltar após o reboot?

Encerre o backend com Ctrl+C no A da Rocky e reinicie uma VM por vez.

```bash
sudo systemctl reboot
```

Na Rocky, após voltar pelo SSH:

```bash
getenforce
getsebool httpd_can_network_connect
systemctl is-active m12a4-nginx
curl --noproxy '*' --max-time 4 -fsS http://127.0.0.1:18094/health
sudo ss -lntp 'sport = :18095'
```

Na Debian:

```bash
sudo aa-status
sudo aa-exec -p m12a4-leitor -- /usr/bin/cat /srv/m12a4-aa/public.txt
sudo aa-exec -p m12a4-leitor -- /usr/bin/cat /srv/m12a4-aa/private.txt
```

**Saída esperada:** Rocky continua enforcing, booleano ativo e nginx próprio respondendo à saúde. O backend temporário não voltou. Na Debian, o perfil carregado no boot mantém a diferença entre os dois arquivos.

**Verifique:** a resposta de saúde usa uma operação que não depende do backend. Não classifique a ausência do Python como falha de persistência da política.

## 6 · Quebre e conserte

### Quebra 1 · Associação local retirada

Somente na Rocky, retire a associação criada nesta aula e reinicie a unidade de exercício.

**Sintoma:** a unidade que funcionava deixa de iniciar na porta de exercício.

**Investigação:** compare personalização local e eventos da tentativa.

```bash
sudo semanage port -d -p tcp 18094
sudo systemctl restart m12a4-nginx
sudo semanage port -l -C
sudo ausearch -m AVC -ts recent -c nginx -i
```

**Causa:** o número continua no arquivo do nginx, mas perdeu a associação local ao tipo adequado.

**Conserto:** readicione apenas essa associação e reinicie a unidade própria.

```bash
sudo semanage port -a -t http_port_t -p tcp 18094
sudo systemctl restart m12a4-nginx
```

**Verifique:** a resposta de `/health` volta sem mudar modo SELinux ou firewall.

**Prevenção:** documente a associação persistente junto da porta configurada no serviço.

### Quebra 2 · Capacidade sem processo de destino

**Sintoma:** após o reboot, a saúde responde, mas o proxy não entrega o conteúdo do backend.

**Investigação:** na Rocky, compare escuta e resposta direta do backend.

```bash
getsebool httpd_can_network_connect
sudo ss -lntp 'sport = :18095'
curl --noproxy '*' --connect-timeout 2 --max-time 4 -fsS http://127.0.0.1:18095/
```

**Causa:** a política continua autorizando a capacidade, mas o Python temporário terminou no reboot. Sem processo de destino, a conexão não pode entregar conteúdo.

**Conserto:** execute novamente no A o comando Python do passo 4. Não amplie a política.

**Verifique:** o proxy volta a entregar `BACKEND ok`.

**Prevenção:** monitore processo e protocolo, além do estado do booleano.

### Quebra 3 · Negativa que é o resultado esperado

**Sintoma:** na Debian, `cat` lê o arquivo de exercício fora do perfil, mas a execução confinada o recusa.

**Investigação:** compare modos, perfil carregado e as duas execuções.

```bash
ls -l /srv/m12a4-aa/private.txt
cat /srv/m12a4-aa/private.txt
sudo aa-exec -p m12a4-leitor -- /usr/bin/cat /srv/m12a4-aa/private.txt
sudo journalctl -k --since '-5 minutes' --no-pager | grep 'm12a4-leitor'
```

**Causa:** o perfil não autoriza esse caminho. A negativa é a política pretendida; a fonte de auditoria pode registrar o evento no journal ou no log de auditoria configurado.

**Conserto:** use o arquivo público autorizado para essa operação. Não altere o modo global nem associe o perfil a todas as execuções do leitor.

**Verifique:** o público responde dentro do perfil, e o privado continua recusado. Ausência no journal não transforma a recusa observada em sucesso.

**Prevenção:** defina o comportamento permitido antes de escrever a regra e teste também a negativa esperada.

### Limpeza

Na Rocky, encerre Python com Ctrl+C. Restaure somente o booleano registrado e retire a instância e as regras que você criou.

```bash
ORIGINAL=$(awk '{print $3}' "$HOME/m12a4/boolean.inicio")
case "$ORIGINAL" in on|off) sudo setsebool -P httpd_can_network_connect "$ORIGINAL" ;; *) printf 'STOP: invalid saved state\n' ;; esac
getsebool httpd_can_network_connect
sudo systemctl disable --now m12a4-nginx
sudo systemctl reset-failed m12a4-nginx
sudo rm -f /etc/systemd/system/m12a4-nginx.service /etc/nginx/m12a4.conf
sudo systemctl daemon-reload
sudo semanage port -d -p tcp 18094
sudo semanage fcontext -d '/var/run/nginx-m12a4(/.*)?'
sudo rm -f /var/log/nginx/m12a4-error.log
```

Se a unidade já tiver parado sem falha, `reset-failed` pode responder que ela não está carregada; isso não é erro.

Na Debian, remova do kernel só o perfil nomeado e depois os arquivos exclusivos. Não descarregue outros perfis.

```bash
sudo apparmor_parser -R /etc/apparmor.d/m12a4-leitor
sudo rm -f /etc/apparmor.d/m12a4-leitor
sudo rm -f /srv/m12a4-aa/public.txt /srv/m12a4-aa/private.txt
sudo rmdir /srv/m12a4-aa
sudo aa-status
```

Guarde as evidências na pasta privada. A unidade nginx original, o firewall e as demais políticas devem permanecer no estado anterior ao exercício.
