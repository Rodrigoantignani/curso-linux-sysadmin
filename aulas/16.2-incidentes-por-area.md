# Aula 16.2 · Incidentes por área

Você já reuniu ferramentas; agora precisa escolher a ferramenta por uma hipótese. Três bancadas pequenas trazem defeitos reais e limitados: um caminho de execução, uma permissão de leitura e um arquivo compactado incompleto. O resto do servidor continua funcionando.

> **Núcleo desta aula:** leia o sintoma, formule uma hipótese verificável, corrija uma causa e peça só a dica necessária para continuar.

| Ficha |  |
| --- | --- |
| **Módulo** | M16 · Semana de incidentes no Rocky 10, aula 2 de 4 |
| **Quando** | Semana 21 |
| **Ao final** | Você isola falhas de caminho, leitura e arquivo compactado e comprova cada reparo após o boot |
| **Pré-requisitos** | M0 a M15; noVNC, sudo, backup e diário de bordo |
| **Tempo** | 60 a 90 minutos; instalação e revisão podem pedir outra sessão |
| **Snapshots** | `m16a2-inicio` e `m16a2-fim`, VMs 205 e 202 |

## 1 · Aquecimento

Responda sem consultar. Compare com as soluções somente no fim.

1. Qual leitura distingue um caminho salvo na unit do comando carregado pelo gerenciador?

2. Quem deve tentar ler o arquivo para reproduzir os privilégios da rotina?

3. Um arquivo compactado com tamanho maior que zero está necessariamente íntegro?

## 2 · Por que importa

Um chamado diz apenas que uma rotina parou. A primeira tentativa de reiniciar não resolve. Você precisa distinguir uma referência que aponta para o lugar errado, uma conta sem leitura e um dado que não pode ser aberto até o fim.

As três falhas são plantadas por um script entregue com a aula. Ele cria e modifica somente arquivos próprios e units exclusivas; não enche discos, altera interfaces, mexe em SSH ou desliga proteções.

## 4 · O essencial

### O contrato da bancada

O script `m16-incidentes.sh` recebe `a2` e uma ação: `setup`, `plant`, `check` ou `cleanup`. Use a mesma versão entregue no pacote nas VMs 205 e 202, após ler o arquivo inteiro.

Ele exige root, usuário `student` existente e hostname `rocky10-lab` ou `debian-lab`. Esse controle reduz enganos de destino, mas não substitui conferir VMID e console. Um hostname pode ser repetido fora do curso.

O preparo recusa caminhos ou units já existentes. Não remova um diretório desconhecido para fazer o script passar. Investigue se é uma tentativa anterior, outra atividade ou um conflito real.

| Objeto | Uso |
| --- | --- |
| `/srv/m16a2` | Conteúdo, configuração e arquivo de teste |
| `/usr/local/libexec/m16a2/run.sh` | Executor dedicado, pertencente a root |
| `/var/lib/m16a2` | Resultados gravados por `student` |
| `m16a2-caminho.service` | Valida caminho e configuração |
| `m16a2-leitura.service` | Valida acesso da conta ao conteúdo |
| `m16a2-arquivo.service` | Percorre o arquivo tar até o fim |

### Um resultado tem contexto

Cada unit executa como `student`, tem início ligado ao boot e usa `Type=oneshot` com `RemainAfterExit=yes`. Depois de terminar com sucesso, ela fica ativa sem manter um processo de trabalho rodando.

O resultado contém o identificador do boot atual. A checagem exige estado ativo, habilitação, caminho carregado correto, validação dos dados e identificador atual. Um arquivo de resultado isolado não basta.

### Dicas que preservam o esforço

Peça primeiro uma pista sobre a camada; depois uma direção de leitura; só então a solução comentada. Registre o nível necessário em cada bancada para planejar o reforço.

Uma dica não deve plantar uma saída fictícia. Os comandos desta aula produzem evidências reais no seu sistema; cite essas evidências ao pedir ajuda.

### O que este treino não simula

Você não vai corromper o boot, preencher a raiz ou remover volumes. Este conjunto treina seleção de evidências nas áreas de serviço, permissões e arquivos. Os incidentes integrados da próxima aula acrescentam dependências entre causas.

## 5 · Lab guiado

Use somente as VMs do contrato. Abra o noVNC antes de começar e confirme o backup. Os comandos de Proxmox pertencem ao host; os demais pertencem à VM indicada.

Na 16.1 crie e valide a VM 205 antes de tirar seu primeiro snapshot. Nas outras aulas ela já deve existir. Nunca aplique um rollback a uma VM diferente para recuperar esta bancada.

```bash
qm snapshot 205 m16a2-inicio
qm snapshot 202 m16a2-inicio
```

Se a recuperação exigir rollback, pare o exercício, abra o console e use o snapshot de início desta aula. Anote o que perdeu e não confunda restauração com diagnóstico concluído.

```bash
qm rollback 205 m16a2-inicio
qm rollback 202 m16a2-inicio
```

### Passo 1 · Ler e transferir o material

**Palpite:** por que você lê um script inteiro antes de executá-lo com sudo?

Transfira `scripts/m16-incidentes.sh` do pacote para a home de `student` em cada VM, por SFTP autenticado. Confira o hash com `SHA256SUMS` do pacote e mantenha o arquivo original para revisão.

```bash
hostname -s
id student
bash -n ~/m16-incidentes.sh
sha256sum ~/m16-incidentes.sh
less ~/m16-incidentes.sh
```

**Saída esperada:** sintaxe válida, hash igual ao manifesto e destinos corretos. Não execute uma cópia truncada ou adaptada sem revisar as diferenças.

**Verifique:** os caminhos alterados pertencem ao contrato e o script não toca em rede, SSH ou discos do sistema.

### Passo 2 · Preparar um estado saudável

**Palpite:** um script de plantio deve funcionar sobre nomes que já pertencem a outra atividade?

Nas duas VMs, rode o preparo uma única vez. Se recusar um objeto existente, pare e investigue. A ação não é um comando para sobrescrever tentativas anteriores.

```bash
sudo bash ~/m16-incidentes.sh a2 setup
sudo bash ~/m16-incidentes.sh a2 check
systemctl list-units 'm16a2-*' --all --no-pager
```

**Saída esperada:** três resultados `PASS`, units ativas e habilitadas. As units não precisam manter processos residentes depois de concluir.

**Verifique:** confira a configuração e as contas efetivas antes de plantar qualquer erro.

```bash
systemctl cat m16a2-caminho.service
systemctl show -p User -p Group -p ExecStart m16a2-leitura.service
```

### Passo 3 · Plantar falhas limitadas

**Palpite:** qual dado antigo precisa deixar de valer quando uma nova tentativa começa?

O plantio interrompe somente estas três units, retira os resultados anteriores e introduz os três defeitos. O comando tenta iniciar cada unit para deixar mensagens reais no journal.

```bash
sudo bash ~/m16-incidentes.sh a2 plant
sudo bash ~/m16-incidentes.sh a2 check
systemctl --failed --no-pager
```

**Saída esperada:** as três bancadas falham. Um retorno não zero da checagem faz parte deste momento e não autoriza ignorar erros depois da correção.

**Verifique:** SSH e os serviços anteriores continuam acessíveis. Registre o primeiro sintoma de cada bancada sem consultar a solução.

### Passo 4 · Separar as evidências

**Palpite:** a mesma leitura explica os três defeitos?

Leia estado, journal e arquivos de cada área. Não edite ainda; procure uma observação que confirme ou descarte sua hipótese.

```bash
systemctl cat m16a2-caminho.service
sudo journalctl -b -u m16a2-caminho.service --no-pager -n 20
namei -l /srv/m16a2/conteudo.txt
sudo -u student cat /srv/m16a2/conteudo.txt
tar -tzf /srv/m16a2/pacote.tar.gz
```

**Saída esperada:** evidência de caminho inexistente, leitura negada à conta e arquivo inválido, respectivamente. A redação e o código exato podem variar; leia sua saída.

**Verifique:** anote hipótese, comando, observação e próxima decisão em quatro campos separados.

### Passo 5 · Corrigir uma causa por vez

**Palpite:** recriar todo o diretório preserva a evidência sobre qual causa você corrigiu?

Tente sozinho. As três soluções comentadas estão na seção seguinte. Depois de cada alteração, reinicie somente a unit correspondente e confira a nova tentativa no journal.

```bash
sudo systemctl restart m16a2-caminho.service
sudo systemctl restart m16a2-leitura.service
sudo systemctl restart m16a2-arquivo.service
sudo bash ~/m16-incidentes.sh a2 check
```

**Saída esperada:** cada causa corrigida faz sua própria bancada passar. As outras falhas continuam visíveis até serem tratadas.

**Verifique:** checagem final devolve zero e três resultados `PASS`. Não altere o script para transformar `FAIL` em aprovação.

### Passo 6 · Repetir a prova num boot novo

**Palpite:** qual falha aparece se uma unit foi iniciada à mão, mas ficou desabilitada?

**Reboot de conferência:** reinicie cada VM pelo console e execute a checagem novamente quando voltar.

```bash
sudo systemctl reboot
```

```bash
sudo bash ~/m16-incidentes.sh a2 check
cat /proc/sys/kernel/random/boot_id
sudo journalctl -b -u m16a2-caminho.service --no-pager
```

**Saída esperada:** as três bancadas passam com resultados do boot atual, sem reinício manual corretivo depois de entrar.

**Verifique:** explique por que o resultado persistiu. Depois faça a limpeza descrita no fechamento, preservando o diário.

## 6 · Quebre e conserte

Trabalhe um defeito por vez. Antes de consultar a correção, escreva o comando que sustentaria a sua hipótese. Não transforme uma dificuldade local numa mudança global.

### Quebra 1 · Caminho de execução

**Sintoma:** `m16a2-caminho.service` não termina com sucesso.

**Investigação:** pista: qual arquivo o Bash recebeu? Direção: compare `ExecStart` com os arquivos de `/usr/local/libexec/m16a2`.

**Causa:** a unit aponta para `ausente.sh`; o executor correto se chama `run.sh`.

**Conserto:** restaure somente a referência da unit dedicada e recarregue o gerenciador.

```bash
sudo sed -i 's|/m16a2/ausente.sh|/m16a2/run.sh|' /etc/systemd/system/m16a2-caminho.service
sudo systemctl daemon-reload
sudo systemctl restart m16a2-caminho.service
```

**Verifique:** `systemctl show -p ExecStart` confirma o caminho carregado e a checagem desta bancada passa.

**Prevenção:** valide a unit e confira referências antes de instalar ou mover um executor.

### Quebra 2 · Conta sem leitura

**Sintoma:** root consegue ler um dado que a rotina não consegue ler.

**Investigação:** pista: quem executa a unit? Direção: compare o modo com a leitura feita por `student`.

**Causa:** o arquivo dedicado recebeu modo `0000`. O executor não roda como root.

**Conserto:** restaure o modo conhecido deste conteúdo público do lab, sem ampliar diretórios ou mudar dono.

```bash
sudo chmod 0644 /srv/m16a2/conteudo.txt
sudo -u student cat /srv/m16a2/conteudo.txt
sudo systemctl restart m16a2-leitura.service
```

**Verifique:** a conta efetiva lê e a unit termina com sucesso.

**Prevenção:** teste acesso com a conta real; não aplique permissões globais como tentativa.

### Quebra 3 · Arquivo que só existe

**Sintoma:** o caminho do arquivo tar existe, mas a leitura completa falha.

**Investigação:** pista: tamanho prova integridade? Direção: liste o conteúdo até o fim e observe o retorno.

**Causa:** o arquivo foi substituído por texto incompleto. Não contém o fluxo gzip e tar esperado.

**Conserto:** recrie somente o arquivo descartável com a origem conhecida deste exercício.

```bash
sudo tar -czf /srv/m16a2/pacote.tar.gz -C /srv/m16a2 conteudo.txt
tar -tzf /srv/m16a2/pacote.tar.gz
sudo systemctl restart m16a2-arquivo.service
```

**Verifique:** a listagem termina sem erro e a bancada passa. Em um backup real, recupere de origem confiável; não recrie dados desconhecidos.

**Prevenção:** teste o arquivo produzido e preserve origem, hash e cópia de recuperação.

## 7 · Armadilhas

- Mudar várias coisas entre duas medições apaga a relação entre causa e resultado.

- Uma mensagem antiga no journal não descreve necessariamente a última tentativa. Use o boot e a unit corretos.

- Um arquivo salvo não garante que o gerenciador tenha carregado a alteração.

- Um comando executado como root não mede as permissões da conta do serviço.

- O script de checagem cobre seu contrato declarado; não promete testar todo o servidor.

## 10 · Checklist e fechamento

### Limpeza

Depois de registrar a checagem pós-boot, remova somente a bancada desta aula nas duas VMs. A limpeza para e desabilita as três units próprias, remove a lista fechada de arquivos e usa `rmdir`, que recusa diretórios com conteúdo extra.

```bash
sudo bash ~/m16-incidentes.sh a2 cleanup
systemctl list-unit-files 'm16a2-*' --no-pager
```

Se houver arquivo extra ou drop-in inesperado, a limpeza deve parar para revisão. Não substitua a recusa por exclusão recursiva. Preserve o script e o diário; a 16.3 usa outra bancada, `m16a3`.

## 11 · Na vida real

Em um servidor que você administra ou tem autorização para observar, faça somente leitura. Identifique a versão, uma unit relevante e o journal do boot atual. Não plante defeitos nem copie os scripts de treino para esse servidor.

```bash
cat /etc/os-release
systemctl --failed --no-pager
journalctl -b -p warning --no-pager -n 30
```

Anote quais dados faltariam para autorizar uma mudança. Não registre senhas, chaves privadas nem conteúdo de usuários.

### Gabarito comentado

**Aquecimento:** compare o arquivo da unit com as propriedades carregadas do gerenciador. Teste a leitura como student, a conta efetiva. Existência e tamanho não validam o fluxo compactado nem sua leitura até o fim.

**Decida 1:** B. O caminho carregado e o arquivo existente permitem confirmar a referência errada antes de mudar permissões ou recriar dados.

**Decida 2:** C. Corrigir uma bancada não corrige automaticamente as outras. Preserve a correção demonstrada e investigue a causa específica da leitura.

1. A recusa protege objetos que podem pertencer a outra atividade. Confira origem, snapshot e contrato; não transforme um conflito desconhecido em exclusão.

2. Restaure somente o nome do executor na unit dedicada, recarregue o gerenciador e confirme o comando carregado antes de reiniciar essa unit.

3. Uma diferença de acesso pela conta efetiva, especialmente o modo plantado no arquivo. Confira também a travessia do caminho; não mude a execução para root.

4. Permissão decide quem lê; integridade decide o que pode ser lido. Recrie apenas o arquivo descartável a partir da origem conhecida e teste a listagem completa.

5. O executor termina e RemainAfterExit mantém o estado ativo após o sucesso. A ausência de processo residente não significa que a execução falhou.

6. As três bancadas devem passar, com units habilitadas e resultados do boot atual, sem reinício manual corretivo. Preserve as evidências antes da limpeza.
