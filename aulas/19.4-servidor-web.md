## 1 · Aquecimento

1. Dois processos podem escutar o mesmo endereço e a mesma porta sem um mecanismo explícito de compartilhamento?

2. Um processo ativo garante que o nome solicitado selecione o site que você imaginou?

3. Um arquivo legível pelo administrador é necessariamente legível pelo processo web?

## 2 · Por que importa

O navegador mostra uma página. Isso ainda não informa qual servidor respondeu, qual site foi escolhido ou de onde veio o conteúdo. Uma página de boas-vindas pode esconder um nome incorreto.

Nesta aula nginx recebe o tráfego isolado e Apache escuta apenas no loopback. Você pode comparar os processos sem provocar uma disputa pela porta pública.

### Ponte Windows

Pense na combinação endereço, porta e nome como recepção, guichê e destinatário. O navegador entrega o nome no pedido; conseguir chegar à recepção não escolhe sozinho o destinatário.

## 3 · Modelo mental

![Nome, porta e raiz respondem perguntas diferentes](../img/19.4-nome-porta-e-raiz.jpg)

*O nome escolhe o site; o caminho e a permissão decidem o arquivo.*

A escuta decide onde o processo recebe conexões. O cabeçalho `Host` participa da seleção do site HTTP. A raiz traduz o caminho solicitado em um arquivo.

Os diretórios ancestrais precisam permitir travessia ao usuário do serviço. Permissão de leitura no arquivo final não compensa um diretório anterior fechado.

No lab, `http://www.lab.test/` chega ao nginx. O caminho `/apache/` é encaminhado ao Apache local; as duas conexões terão registros distintos.

### Rocky × Debian

O caminho principal é Debian: pacote e unidade `apache2`, usuário `www-data`. No Rocky, Apache usa pacote e unidade `httpd`, usuário `apache`; nginx usa o usuário `nginx`.

Não cole a configuração principal do Debian no Rocky. Primeiro leia a configuração carregada e o manual da família; os nomes de usuário e os pontos de inclusão mudam.

## 5 · Lab guiado

Execute os passos 1–6 no console da VM `204`, como root. Os clientes só fazem pedidos de leitura. Nunca use um nome de interface adivinhado.

### Passo 1 · Instalar sem abrir a gestão

**Palpite:** A instalação pode iniciar um serviço antes de você limitar a escuta?

```bash
set -eu
test ! -L /etc/m19-lab.env
test "$(stat -c '%U:%G:%a' /etc/m19-lab.env)" = root:root:644
cat /etc/m19-lab.env
. /etc/m19-lab.env
test "$LAB_IP" = 192.0.2.204
ip -4 -o address show dev "$LAB_IF" | grep -F '192.0.2.204/24'
for pkg in nginx apache2; do
  if dpkg-query -W -f='${Status}' "$pkg" 2>/dev/null | grep -q 'install ok installed'; then
    printf '%s\n' "STOP: $pkg already installed" >&2; exit 1
  fi
done
test ! -e /etc/nginx/nginx.conf
test ! -e /etc/apache2/apache2.conf
for unit in nginx apache2; do
  test "$(systemctl is-enabled "$unit" 2>/dev/null || true)" != masked
done
EVID=/root/m19a4
test ! -e "$EVID"
install -d -m 700 "$EVID"
systemctl mask nginx.service apache2.service
apt-get update
apt-get install -y nginx apache2 curl
cp -a /etc/nginx /etc/apache2 "$EVID/"
```

**Saída esperada:** Os pacotes estão instalados; as unidades continuam mascaradas. Se a guarda interromper, investigue antes de prosseguir.

**Verifique:** Confirme que a interface é a isolada e que o console permanece acessível. Um bloqueio de instalação exige resolver a causa, sem desmascarar o serviço incompleto.

### Passo 2 · Preparar conteúdo dedicado

**Palpite:** Qual usuário precisa ler o arquivo e atravessar os diretórios?

```bash
test ! -e /srv/www/m19-web
install -d -m 755 /srv/www/m19-web
printf '%s\n' 'M19 web: OK' > /srv/www/m19-web/index.html
chmod 644 /srv/www/m19-web/index.html
namei -l /srv/www/m19-web/index.html
runuser -u www-data -- cat /srv/www/m19-web/index.html
```

**Saída esperada:** O leitor do serviço obtém o marcador do lab sem se tornar dono da árvore.

**Verifique:** Registre dono e modo. Conteúdo estático não exige que o processo web possa escrever na raiz publicada.

### Passo 3 · Separar a porta do Apache

**Palpite:** Uma escuta em loopback deve aparecer como acessível de outra VM?

```bash
printf '%s\n' 'Listen 127.0.0.1:8081' > /etc/apache2/ports.conf
a2dissite 000-default
cat > /etc/apache2/sites-available/m19-web.conf <<'EOF'
<VirtualHost 127.0.0.1:8081>
    ServerName www.lab.test
    DocumentRoot /srv/www/m19-web
    <Directory /srv/www/m19-web>
        Require all granted
    </Directory>
    ErrorLog /var/log/apache2/m19-error.log
    CustomLog /var/log/apache2/m19-access.log combined
</VirtualHost>
EOF
a2ensite m19-web
apache2ctl configtest
```

**Saída esperada:** O teste de sintaxe aceita a configuração; o serviço ainda está mascarado. Uma advertência de nome global deve ser distinguida de erro fatal.

**Verifique:** Leia o arquivo de portas inteiro. Não mantenha uma segunda diretiva de escuta pública deixada pelo pacote.

### Passo 4 · Selecionar o site no nginx

**Palpite:** Como evitar que um nome errado receba a página correta por acaso?

```bash
test -z "$(find /etc/nginx/conf.d -maxdepth 1 -name '*.conf' -print -quit)"
cat > /etc/nginx/nginx.conf <<'EOF'
user www-data;
worker_processes auto;
pid /run/nginx.pid;
error_log /var/log/nginx/error.log;
include /etc/nginx/modules-enabled/*.conf;
events { worker_connections 512; }
http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;
    include /etc/nginx/conf.d/*.conf;
}
EOF
cat > /etc/nginx/conf.d/m19-web.conf <<EOF
server {
    listen $LAB_IP:80 default_server;
    server_name _;
    return 404;
}
server {
    listen $LAB_IP:80;
    server_name www.lab.test web.lab.test;
    root /srv/www/m19-web;
    index index.html;
    allow 192.0.2.0/24;
    deny all;
    access_log /var/log/nginx/m19-access.log;
    error_log /var/log/nginx/m19-error.log;
    location /apache/ {
        proxy_pass http://127.0.0.1:8081/;
    }
}
EOF
nginx -t
systemctl unmask nginx.service apache2.service
systemctl enable --now apache2 nginx
```

**Saída esperada:** nginx ocupa somente o endereço isolado na porta 80; Apache ocupa somente o loopback na 8081.

**Verifique:** Se houver firewall anterior, adapte uma regra restrita à interface e rede isoladas com o procedimento da 19.1; não limpe regras nem abra a zona de gestão.

### Passo 5 · Relacionar pedido e registros

**Palpite:** O mesmo arquivo obtido por dois caminhos prova que os processos são iguais?

```bash
ss -ltnp '( sport = :80 or sport = :8081 )'
curl --fail --resolve www.lab.test:80:192.0.2.204 http://www.lab.test/
curl --fail --resolve www.lab.test:80:192.0.2.204 http://www.lab.test/apache/
curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: wrong.lab.test' http://192.0.2.204/
tail -n 5 /var/log/nginx/m19-access.log
tail -n 5 /var/log/apache2/m19-access.log
```

**Saída esperada:** Os dois pedidos corretos recebem o marcador. O nome não configurado recebe 404; somente o pedido encaminhado chega ao registro do Apache.

**Verifique:** Repita os dois pedidos corretos da VM `201` ou `202`. O acesso à porta `8081` de fora deve falhar, pois ela pertence ao loopback.

### Passo 6 · Investigar a proteção sem removê-la

**Palpite:** Se a leitura local funciona, uma política ainda pode negar o serviço?

```bash
systemctl is-active nginx apache2
journalctl -u nginx -u apache2 -b --no-pager -n 30
command -v aa-status >/dev/null && aa-status || true
stat -c '%U:%G %a %n' /srv/www/m19-web /srv/www/m19-web/index.html
```

**Saída esperada:** Você identifica quais controles estão presentes; não presume um perfil AppArmor carregado só por estar no Debian.

**Verifique:** No Rocky comparativo, leia o contexto e as negativas antes de definir o rótulo persistente abaixo, apenas na árvore dedicada.

```bash
getenforce
ls -Zd /srv/www/m19-web
semanage fcontext -l | grep -F '/srv/www/m19-web' || true
semanage fcontext -a -t httpd_sys_content_t '/srv/www/m19-web(/.*)?'
restorecon -Rv /srv/www/m19-web
sudo ausearch -m AVC -ts recent || true
```

Esse bloco pertence somente ao Rocky com a árvore criada e sem regra local anterior. Se a regra já existir, confira-a em vez de adicionar outra. A porta `8081` permanece no lab Debian. No comparativo Rocky use `8008`, depois de confirmar que pertence a `http_port_t`, está livre e não atende outra aplicação. Configure ali Listen e VirtualHost em `127.0.0.1:8008` e ajuste apenas o upstream do comparativo Rocky; não altere o lab Debian. `8081` pode ser `transproxy_port_t` e não autorizar o bind do Apache.

Leia `semanage port -l` e use somente uma porta autorizada ao processo ou uma atribuição específica previamente revisada. Não recategorize uma porta de outro serviço e não desligue SELinux para fazer a comparação.

Após o relabel, nenhuma correspondência AVC é o resultado esperado: ausearch retorna 1 nesse caso. O sufixo do comando evita aborto com set -e; erros diferentes na leitura do audit ainda precisam ser investigados. Confira as portas com `sudo semanage port -l` antes do comparativo Rocky.

## 6 · Quebre e conserte

Faça um defeito por vez na VM `204`, registre o retorno e restaure antes do próximo. Os comandos de restauração atuam só nos objetos dedicados desta aula.

### Quebra 1 · Arquivo fechado

**Sintoma:** Aplique `chmod 000 /srv/www/m19-web/index.html`; o pedido correto recebe 403.

**Investigação:** Leia o erro nginx e `namei -l /srv/www/m19-web/index.html`.

**Causa:** O modo impede a leitura pelo usuário do serviço; a seleção do site continua correta.

**Conserto:** Restaure com `chmod 644 /srv/www/m19-web/index.html`.

**Verifique:** Repita o pedido com o mesmo nome e confira o marcador.

**Prevenção:** Mantenha escrita administrativa e leitura mínima do serviço, sem permissões totais.

### Quebra 2 · Backend parado

**Sintoma:** Pare apenas `apache2` com `systemctl stop apache2`; `/apache/` retorna 502.

**Investigação:** Confira `ss`, o erro nginx e o estado do Apache. A raiz estática ainda responde.

**Causa:** O frontend recebeu o pedido, mas a conexão ao upstream local falhou.

**Conserto:** Execute `systemctl start apache2`; não altere o nome nem a raiz do nginx.

**Verifique:** Repita o caminho encaminhado e procure sua nova entrada nos dois registros.

**Prevenção:** Monitore a dependência por resposta, além do processo frontend.

### Quebra 3 · Nome inesperado

**Sintoma:** Peça `wrong.lab.test` com o mesmo endereço e observe 404.

**Investigação:** Compare o nome enviado e os blocos de servidor lidos por `nginx -T`.

**Causa:** O servidor padrão rejeita nomes que não pertencem ao site do lab.

**Conserto:** Corrija o nome do pedido para `www.lab.test`; não transforme o padrão em aceitação universal.

**Verifique:** O nome correto recebe o marcador e o incorreto permanece rejeitado.

**Prevenção:** Teste um nome válido e um inválido ao revisar um virtual host.

## 7 · Armadilhas

![Um arquivo passa por mais de uma proteção](../img/19.4-duas-portarias-do-arquivo.jpg)

*Investigue a negativa; preserve as proteções do sistema.*

A saída de `nginx -T` descreve arquivos carregados, mas pode conter dados operacionais. Examine localmente e não a publique inteira sem revisão.

Uma resposta 403 pode vir de permissão, política, regra de acesso ou ausência de índice. O código restringe a investigação; sozinho não escolhe o conserto.

Uma porta aberta na gestão não é compensada por um nome bonito no DNS. O endereço de escuta limita a superfície antes da seleção HTTP.

Depois de corrigir uma negativa, confira também uma operação que deve continuar proibida. Recuperar o serviço não exige ampliar a superfície de acesso.

### Quiz · Respostas por pergunta

1. O nome seleciona o virtual host; a raiz e as proteções determinam a leitura do arquivo.

2. Apache está ligado somente ao loopback, em porta diferente da entrada nginx.

3. O pedido ao caminho encaminhado, a conexão ao upstream e os registros dos dois serviços.

4. Quando uma negativa permanece apesar de caminho, identidade e modo coerentes, confira contexto e AVC; o registro pode apontar diretamente para a política.

5. Execução nos diretórios permite travessia; leitura no arquivo permite obter o conteúdo.
