Aula 6.5 · Bibliotecas compartilhadas

Quase nenhum programa do Linux funciona sozinho. O ls, o sshd e o dnf carregam, na hora em que rodam, bibliotecas que ficam em outros arquivos: a libc, a libssl, a libz. Quando uma delas falta, está na pasta errada ou é a versão errada, aparece a mensagem que todo sysadmin já viu: error while loading shared libraries. Esta aula ensina a ler essa mensagem e resolver do jeito certo. No fim vem o Desafio do M6.

Núcleo desta aula: entender os três nomes de uma biblioteca (real name, soname, linker name); ver as dependências de um programa com ldd e readelf; saber onde o loader procura; registrar uma pasta nova com /etc/ld.so.conf.d e ldconfig; e saber por que LD_LIBRARY_PATH e symlink improvisado são remendos. O resto é aprofundamento.

3 · Modelo mental

O programa é uma lista de convidados: no binário está escrito "preciso da libz.so.1 e da libc.so.6", só o nome, sem endereço. Quem vai buscar cada um é o loader (ld-linux), e ele procura numa ordem fixa. A agenda dele é o /etc/ld.so.cache, que o ldconfig monta a partir da lista de pastas em /etc/ld.so.conf.d. Se a pasta não está na lista e ninguém atualizou a agenda, o loader não acha, mesmo com o arquivo lá.

./programa
   │  o kernel lê o ELF: "interpretador: /lib64/ld-linux-x86-64.so.2"
   ▼
ld-linux (o loader)
   │  para cada NEEDED gravado no binário (ex.: libz.so.1):
   ├─ 1. RUNPATH/RPATH gravado no próprio binário
   ├─ 2. LD_LIBRARY_PATH (variável de ambiente)
   ├─ 3. /etc/ld.so.cache  ← o ldconfig gera a partir de /etc/ld.so.conf(.d)
   └─ 4. pastas padrão: /lib64 e /usr/lib64 (Rocky)
                        /lib/x86_64-linux-gnu e /usr/lib/x86_64-linux-gnu (Debian)
   ▼
não achou → "error while loading shared libraries: libz.so.1:
            cannot open shared object file: No such file or directory"

O detalhe fino: o RPATH antigo vem antes do LD_LIBRARY_PATH e o RUNPATH moderno vem depois. Para o dia a dia, basta a ordem do desenho.

4 · O essencial

Os três nomes

NomeExemploO que éQuem cria
Real namelibz.so.1.2.13O arquivo de verdade, com a versão completaO pacote (zlib / zlib1g)
Sonamelibz.so.1Symlink para o real name. É o nome que fica gravado nos programas. Só muda quando a interface quebraO ldconfig (e o pacote)
Linker namelibz.soSymlink usado só para compilar (-lz)O pacote de desenvolvimento (zlib-devel / zlib1g-dev)

A regra que explica tudo: mesmo soname, interface compatível. A libz.so.1.2.13 e a libz.so.1.3.1 têm o mesmo soname libz.so.1, então qualquer programa feito para uma usa a outra. Uma libz.so.2 seria outra interface, e os programas antigos continuariam pedindo a .so.1.

Na Rocky, /lib64 é symlink para /usr/lib64. No Debian moderno, /lib é symlink para /usr/lib. Em ambos, a pasta "de verdade" é a que está em /usr.

5 · Lab guiado

Você vai criar uma biblioteca de brinquedo, a libola, e quebrar e consertar o carregamento dela de vários jeitos.

Passo 0 · Snapshot, pasta e compilador. No Proxmox: qm snapshot 201 m6a5-inicio. Na rocky-lab:

sudo dnf install -y gcc
mkdir -p ~/lab65 && cd ~/lab65

Passo 1 · Olhar um programa de verdade.

ldd /usr/bin/ls
readelf -d /usr/bin/ls | grep NEEDED
ls -l /usr/lib64/libz.so*
rpm -qf /usr/lib64/libz.so.1
ldconfig -p | grep libz
cat /etc/ld.so.conf
ls /etc/ld.so.conf.d/

O readelf mostra só os nomes (sonames). O ldd mostra também onde cada um foi achado. No ls -l, repare na cadeia de symlinks: libz.so.1 aponta para o real name. O libz.so (linker name) só existe se o zlib-devel estiver instalado.

Passo 2 · Criar a biblioteca e um programa que usa ela.

cat > ola.c <<'EOF'
#include <stdio.h>
void ola(void) { puts("ola da biblioteca v1"); }
EOF

cat > main.c <<'EOF'
void ola(void);
int main(void) { ola(); return 0; }
EOF

gcc -fPIC -shared -Wl,-soname,libola.so.1 -o libola.so.1.0 ola.c
ln -s libola.so.1.0 libola.so
gcc -o app main.c -L. -lola
./app

O -Wl,-soname,libola.so.1 grava o soname dentro da lib. O ln -s cria o linker name, que o gcc -lola usa para compilar. E o ./app falha: error while loading shared libraries: libola.so.1: cannot open shared object file.

Passo 3 · Diagnosticar e testar sem instalar.

ldd ./app | grep ola
readelf -d app | grep NEEDED
ls -l
LD_LIBRARY_PATH=. ./app
ldconfig -n .
ls -l
LD_LIBRARY_PATH=. ./app

O ldd mostra libola.so.1 => not found. O binário pede a libola.so.1 (o soname), não a libola.so.1.0 nem a libola.so. Por isso o primeiro LD_LIBRARY_PATH=. ainda falha: não existe arquivo com esse nome na pasta. O ldconfig -n . cria o symlink de soname só nesta pasta, sem mexer na agenda do sistema. Agora o teste funciona. Mas ele vale só para esse comando.

Passo 4 · Instalar do jeito certo.

sudo mkdir -p /opt/ola/lib
sudo cp libola.so.1.0 /opt/ola/lib/
./app
echo /opt/ola/lib | sudo tee /etc/ld.so.conf.d/ola.conf
sudo ldconfig
ls -l /opt/ola/lib
ldconfig -p | grep ola
ldd ./app | grep ola
./app

O primeiro ./app continua falhando: o arquivo está lá, mas a pasta não está na agenda. Depois do ldconfig, duas coisas mudaram: a agenda conhece a pasta, e o ldconfig criou sozinho o symlink libola.so.1 -> libola.so.1.0.

Passo 5 · Versões: compatível e incompatível.

sed 's/v1/v1.1/' ola.c > ola11.c
gcc -fPIC -shared -Wl,-soname,libola.so.1 -o libola.so.1.1 ola11.c
sudo cp libola.so.1.1 /opt/ola/lib/
sudo ldconfig
ls -l /opt/ola/lib
./app

Mesmo soname, versão maior: o ldconfig passou o symlink libola.so.1 para a 1.1, e o app usa a nova sem recompilar. É assim que uma correção de segurança na openssl-libs chega a todos os programas de uma vez.

sed 's/v1/v2/' ola.c > ola2.c
gcc -fPIC -shared -Wl,-soname,libola.so.2 -o libola.so.2.0 ola2.c
sudo cp libola.so.2.0 /opt/ola/lib/
sudo ldconfig
ls -l /opt/ola/lib
ldconfig -p | grep ola
./app

Soname novo, interface nova: agora existem libola.so.1 e libola.so.2 lado a lado, e o app antigo continua com a 1.1. Só um programa compilado de novo, contra a .so.2, usaria a versão 2. Por isso a Rocky 9 pode ter a libssl.so.3 e, num pacote de compatibilidade, a libssl.so.1.1 ao mesmo tempo.

Passo 6 · RUNPATH: o binário que diz onde procurar.

gcc -o app-local main.c -L. -lola -Wl,-rpath,'$ORIGIN'
readelf -d app-local | grep -E 'NEEDED|RUNPATH'
./app-local
./app

O $ORIGIN quer dizer "a pasta onde o binário está". O app-local acha a libola.so.1 de ~/lab65 (a v1) antes de olhar a agenda, enquanto o app usa a 1.1 do sistema. Muitos apps de fornecedor em /opt vêm assim, com as próprias libs ao lado.

Passo 7 · debian-lab, só leitura.

ldd /usr/bin/ls
ls -l /usr/lib/x86_64-linux-gnu/libz.so*
dpkg -S libz.so.1
cat /etc/ld.so.conf.d/*.conf

Mesma ideia, pasta multiarch diferente. O pacote se chama zlib1g: o 1 é o soname.

Não limpe ainda. As quebras da seção 6 usam o /opt/ola. A limpeza vem no fim delas.

Decida 1

Um app de fornecedor em /opt/vendor não sobe numa Rocky 9: libssl.so.1.1: cannot open shared object file. A Rocky 9 tem a libssl.so.3. O que você faz?

A) ln -s /usr/lib64/libssl.so.3 /usr/lib64/libssl.so.1.1. B) Instala o pacote de compatibilidade da distribuição (dnf provides 'libssl.so.1.1()(64bit)', na Rocky 9 é o compat-openssl11) e cobra do fornecedor uma versão para OpenSSL 3. C) Baixa uma libssl.so.1.1 de um site qualquer e joga em /usr/lib64.

Marque uma opção antes.

Se você marcouResultadoPor quê
ASobe e cai depois, ou pior, funciona erradoSoname diferente quer dizer interface diferente. O symlink engana o loader, não o código
BCertoLib com o soname certo, assinada, atualizada pelo dnf, e o problema de verdade (app velho) fica registrado
CPior de todasBiblioteca de criptografia de origem desconhecida, fora de qualquer atualização

Para fixar: quando falta um soname, procure quem fornece aquele soname. Nunca aponte um soname para outro.

Decida 2

O app em /opt/app traz em /opt/app/lib as próprias cópias de várias libs, inclusive uma libcrypto.so.3 mais antiga que a do sistema. Um colega resolveu com export LD_LIBRARY_PATH=/opt/app/lib no /etc/profile. O app roda como serviço do systemd. O que você faz?

A) Deixa como está, funcionou. B) Troca por /etc/ld.so.conf.d/app.conf com /opt/app/lib e roda ldconfig. C) Remove do /etc/profile e coloca a variável só no serviço: Environment=LD_LIBRARY_PATH=/opt/app/lib no unit (ou um script que exporta e chama o app).

Marque uma opção antes.

Se você marcouResultadoPor quê
AErrado duas vezesO /etc/profile vale para logins, não para o serviço. E todo programa que você abrir no shell passa a usar a libcrypto velha do app
BPerigoso aquiAs pastas do ld.so.conf.d entram na agenda antes das pastas padrão. O sistema inteiro, incluindo sshd e dnf, passaria a usar a libcrypto velha
CCertoSó o app enxerga as libs dele

Para fixar: ld.so.conf.d é para pasta com libs que só existem ali. Pasta com cópias de libs do sistema fica restrita ao app que precisa dela.

6 · Quebre e conserte

Quebra 1 · Agenda desatualizada

sudo rm /opt/ola/lib/libola.so.1
./app
ldconfig -p | grep ola

Sintoma: cannot open shared object file, embora a libola.so.1.1 esteja lá.

Diagnóstico: a agenda ainda diz que a libola.so.1 está em /opt/ola/lib, mas ls -l /opt/ola/lib mostra que o symlink de soname sumiu. O loader procura pelo soname, não pelo arquivo com versão.

Conserto: sudo ldconfig. Ele recria o symlink e a agenda. Confira com ls -l e ./app.

Na vida real: acontece quando alguém copia uma lib à mão, ou um script de instalação apaga e recopia arquivos. Sempre que mexer em lib fora do gerenciador de pacotes: sudo ldconfig.

Quebra 2 · A biblioteca impostora

mkdir -p ~/lab65/falsa
sed 's/v1/IMPOSTORA/' ~/lab65/ola.c > ~/lab65/falsa.c
gcc -fPIC -shared -Wl,-soname,libola.so.1 -o ~/lab65/falsa/libola.so.1 ~/lab65/falsa.c
export LD_LIBRARY_PATH=~/lab65/falsa
./app
ldd ./app | grep ola
sudo ./app
unset LD_LIBRARY_PATH
./app

Sintoma: o app imprime IMPOSTORA. Com sudo, volta ao normal.

Diagnóstico: echo $LD_LIBRARY_PATH e ldd ./app mostram a lib vindo de ~/lab65/falsa. A variável passa na frente da agenda.

Conserto: unset LD_LIBRARY_PATH, e procurar onde ela foi definida (~/.bashrc, /etc/profile.d/, /etc/environment).

Na vida real: é por isso que o sudo limpa o ambiente, e que programas setuid ignoram o LD_LIBRARY_PATH. Se ele valesse para root, qualquer usuário trocaria a libc do passwd por uma dele.

Quebra 3 · Removeram uma lib do sistema (narrativa)

Alguém rodou rpm -e --nodeps openssl-libs para "reinstalar limpo". Na hora, ssh, curl e dnf param com libcrypto.so.3: cannot open shared object file. O dnf não consegue reinstalar porque ele próprio precisa da lib.

Diagnóstico: ldd /usr/bin/curl | grep 'not found' e rpm -V openssl-libs.

Conserto: se o rpm ainda roda, rpm -ivh do pacote tirado da ISO (é para isso que serve o repositório da ISO da aula 6.3). Se nem ele roda, boot pela ISO no modo rescue e rpm --root=/mnt/sysroot -ivh ....

Para fixar: --nodeps desliga exatamente a proteção que impede isso. Quase nunca é a resposta.

Limpeza

unset LD_LIBRARY_PATH
sudo rm /etc/ld.so.conf.d/ola.conf
sudo rm -r /opt/ola
sudo ldconfig
ldconfig -p | grep ola

O último comando não deve mostrar nada. A pasta ~/lab65 pode ficar.

11 · Na vida real

Missão, só leitura. Num servidor Linux que você administre (ou com autorização), rode apenas:

cat /etc/ld.so.conf
cat /etc/ld.so.conf.d/*.conf
/usr/sbin/ldconfig -p | wc -l
ls -l /etc/ld.so.preload 2>/dev/null
grep -rs LD_LIBRARY_PATH /etc/profile /etc/profile.d/ /etc/environment /etc/systemd/system/
sudo dnf needs-restarting -s 2>/dev/null || sudo needrestart -b 2>/dev/null

Perguntas para responder:

  1. Que pastas extras estão registradas, e de que pacote ou app vem cada uma?
  2. Alguma delas tem cópias de libs do sistema (libssl, libcrypto, libz)? Confira com ls.
  3. Existe /etc/ld.so.preload? Num servidor comum não deveria existir. Se existir e você não souber de onde veio, é caso de investigar: é um lugar clássico de rootkit.
  4. Alguém usa LD_LIBRARY_PATH globalmente ou num unit?
  5. Há serviços que precisam ser reiniciados depois da última atualização?

Diário: anote a resposta da 5. Se houver serviços pendentes, isso vira uma tarefa de manutenção agendada. Não reinicie nada agora.

Amanhã, sem olhar: escreva a ordem de busca do loader e os dois comandos para registrar uma pasta nova.

12 · Aprofundar quando quiser

  • man ld.so e man ldconfig: a ordem de busca exata, RPATH × RUNPATH e o modo seguro dos programas setuid.
  • LD_PRELOAD e /etc/ld.so.preload: carregar uma lib antes de todas. É usado para depuração e também por malware.
  • Versionamento de símbolos: o erro version `GLIBC_2.34' not found aparece quando você leva um binário de um sistema novo para um velho.
  • Estático × dinâmico: por que Go gera binários quase estáticos e por que a distribuição prefere o dinâmico (uma correção vale para todos).
  • patchelf: mudar o RUNPATH de um binário pronto.
  • lddtree (pacote pax-utils): a árvore de dependências inteira, sem executar o binário.

Desafio do M6 · Instalação offline

A missão: a rocky-lab instala pacotes sem internet, usando só a ISO como repositório, e continua assim depois do reboot.

Na aula 6.3 você montou a ISO à mão e fez um repositório temporário. Agora o resultado tem que ser permanente, e quem confere é o reboot. Não há passo a passo. As dicas estão no Gabarito, mas tente sem elas primeiro.

Antes de começar:

  • Confira que a ISO anexada à VM é a DVD (Rocky-9.x-x86_64-dvd.iso), não a minimal. A minimal tem poucos pacotes. Teste: dnf --repo=iso-appstream list --available | wc -l.
  • Faça qm snapshot 201 m6-desafio-inicio.

Requisitos:

  1. A ISO monta sozinha em /mnt/iso no boot, pelo /etc/fstab, somente leitura. Se a ISO não estiver anexada, o boot não pode travar.
  2. Um arquivo /etc/yum.repos.d/local-iso.repo com os repositórios BaseOS e AppStream da ISO, com gpgcheck=1 e a chave certa.
  3. Todos os repositórios de rede desligados de forma permanente: baseos, appstream, extras, crb, epel e qualquer outro que apareça. Não vale --disablerepo na linha de comando.
  4. Sem internet de verdade durante o teste: sudo ip route del default (volta no reboot).
  5. Instalar um pacote do BaseOS (por exemplo zsh) e um do AppStream (por exemplo git) que ainda não estejam instalados.
  6. sudo dnf check-update e sudo dnf makecache terminam rápido e sem erro, sem tentar a internet.

Critérios de aceite (depois de um sudo reboot):

findmnt /mnt/iso
dnf repolist
sudo ip route del default
sudo dnf makecache
sudo dnf install -y zsh git
rpm -q zsh git
sudo dnf check-update; echo "saida=$?"
  • [ ] O findmnt mostra a ISO em /mnt/iso, com ro
  • [ ] O dnf repolist mostra só os dois repositórios da ISO
  • [ ] Instalou os dois pacotes com a rota padrão removida
  • [ ] O check-update termina em segundos (saída 0 ou 100, sem erro de rede)
  • [ ] Com a ISO desanexada (qm set 201 --ide2 none,media=cdrom), a VM ainda dá boot

Bônus (opcional):

  • Repositório próprio: junte alguns .rpm em /srv/repo-local, gere os metadados com createrepo_c (instale o pacote antes de cortar a rede) e crie um .repo para ele. Você acabou de fazer um mini mirror.
  • Debian: na debian-lab, faça o equivalente com a ISO DVD 1 do Debian e apt-cdrom add, ou com uma linha .sources apontando para file:/mnt/iso.

Ao terminar: qm snapshot 201 m6-desafio-fim. Os próximos módulos precisam de internet. Volte para o estado normal com qm rollback 201 m6a5-fim. O snapshot do Desafio fica guardado como prova.

Você fechou o M6. Agora você instala, consulta, verifica e remove pacotes nas duas famílias, mexe em repositórios, usa Flatpak e resolve biblioteca que não carrega. O próximo módulo está na aba Plano.

Gabarito comentado

Aquecimento

  1. Quase tudo para. O ls, o rm, o bash e o dnf dependem da libc.so.6. Qualquer comando novo falha ao carregar. Só os builtins do shell que já está aberto continuam (echo, cd). O caminho é boot pela ISO no modo rescue e reinstalar a glibc com rpm --root. É o exemplo mais extremo da Quebra 3.
  2. Cada nome tem uma função. libz.so.1.2.13 é o arquivo (real name). libz.so.1 é o soname, que os programas pedem. libz.so é o linker name, que só o compilador usa.
  3. A pasta não está na agenda do loader. Ele não varre o disco, ele consulta o /etc/ld.so.cache e as pastas padrão. Ou você registra a pasta (ld.so.conf.d + ldconfig), ou o binário traz o RUNPATH, ou você usa o LD_LIBRARY_PATH só para aquele programa. E confira se o arquivo com o nome do soname existe ali.

Quiz

  1. O real name (libfoo.so.1.4.2) é o arquivo, e quem cria é o pacote. O soname (libfoo.so.1) é o symlink com o nome que fica gravado nos programas; quem cria é o ldconfig (e o pacote). O linker name (libfoo.so) serve para compilar com -lfoo, e vem no pacote -devel ou -dev.
  2. Temporário: LD_LIBRARY_PATH=/opt/x/lib ./programa. Permanentes: um arquivo em /etc/ld.so.conf.d/ mais sudo ldconfig, ou o binário compilado com RUNPATH (-Wl,-rpath,..., ou patchelf num binário pronto). Num serviço, também vale Environment=LD_LIBRARY_PATH= no unit.
  3. Porque o ldd pode acabar executando o binário para descobrir as dependências, e um binário malicioso aproveita isso. Use readelf -d ou objdump -p, que só leem o arquivo.
  4. Porque soname diferente quer dizer interface diferente: funções que mudaram de assinatura ou sumiram. O loader aceita o symlink, mas o programa chama coisas que não existem mais ou que funcionam de outro jeito. O certo é instalar a lib com o soname .so.1 (pacote de compatibilidade) ou atualizar o app.
  5. O LD_LIBRARY_PATH (ou outra variável) definido no seu ~/.bashrc ou no /etc/profile. O systemd não lê esses arquivos. Confira com systemctl show SERVICO -p Environment e com o journalctl -u SERVICO.
  6. b) /etc/ld.so.conf (que no Rocky e no Debian só inclui o /etc/ld.so.conf.d/*.conf). O a) é a agenda binária que o ldconfig gera. O c) não existe. O d) é a lista de libs pré-carregadas.

Dicas do Desafio

Leia uma de cada vez, só quando travar.

  1. fstab: o formato é dispositivo ponto tipo opções dump pass. Para a ISO no drive de CD da VM: /dev/sr0 /mnt/iso iso9660 ro,nofail 0 0. O nofail é o que impede o boot de travar sem a ISO.
  2. Antes de reiniciar: sudo umount /mnt/iso, depois sudo mount -a e findmnt --verify. Se o mount -a reclamar, o reboot também vai reclamar.
  3. O .repo: é o mesmo da aula 6.3, com baseurl=file:///mnt/iso/BaseOS e file:///mnt/iso/AppStream, enabled=1, gpgcheck=1 e gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-Rocky-9.
  4. Desligar os de rede: primeiro veja todos com dnf repolist --all. O EPEL costuma trazer mais de um repositório. Depois sudo dnf config-manager --set-disabled baseos appstream extras crb epel ... e confira com dnf repolist de novo.
  5. Cache velho: se o dnf ainda tentar a rede, rode sudo dnf clean all e sudo dnf makecache.
  6. git não aparece: confirme que é a ISO DVD (ls /mnt/iso/AppStream/Packages | wc -l deve dar alguns milhares).
  7. createrepo_c (bônus): instale antes de cortar a rede. Depois, sudo createrepo_c /srv/repo-local e um .repo com baseurl=file:///srv/repo-local. Como os pacotes vieram assinados, gpgcheck=1 continua valendo.
